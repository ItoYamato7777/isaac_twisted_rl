# 依頼: Claude Code で開発を続けるための基盤づくりと、リポジトリの大規模リファクタリング

## 0. この依頼の読み方

この作業は複数のセッションにまたがり、途中でコンテキストの圧縮も起きる。そこで最初に次の 2 つを行うこと。

1. この依頼文の全文を `refactor/BRIEF.md` に保存する。保存先が Phase 0 で決まるまでは scratchpad に置く。
   以後、依頼の解釈に迷ったときは、記憶に頼らずこのファイルを読み直す。
2. 本文の印は次の意味で使う。
   - 【必須】破ってはいけない。守れない事情があるときは作業を止めて私に報告する。
   - 【方針】原則として従う。従わない方がよいと判断したら、理由を記録したうえで逸脱してよい。逸脱したことは報告に含める。
   - 【叩き台】例や初期案。リポジトリの実態に合わせて変えてよい。変えることを期待している。

### 最重要の原則 (迷ったらここに戻る)

1. 【必須】学習・評価の挙動、Gym のタスク ID、ログとチェックポイントとの互換性を、承認なしに変えない。
2. 【必須】確認できた事実だけを書く。確認できないことは「未確認」と書く。
   subagent の報告も、根拠のファイル:行を自分で確かめるまでは未確認として扱う。
3. 【必須】再現に必要な情報 (commit・seed・iteration・コマンド・ログのパス) を失わない。
   `logs/` は git 管理外なので、文書から消えた情報は二度と戻らない。
4. 【方針】作るより減らす。ファイル・規則・skill・hook は、実際に起きた失敗か、実際に繰り返された手順を根拠に持つものだけ作る。
   根拠のない雛形は、将来の Claude にとって読む量を増やすだけになる。
5. 【方針】規則は、守らせる仕組みのうち最も確実な場所に置く (§5)。文書に書くのは最後の手段にする。

## 1. 背景と目的

あなたはこのリポジトリ (isaac_twisted_rl: Isaac Lab 上のロープ結びの強化学習の研究コード) のリファクタリング担当です。
このリポジトリは今後も Claude Code が主な開発者になる。

現状では、新しいセッションの Claude が現在地を知るには、数百行の引き継ぎメモや計画書を読む必要がある。
そのうえ、開発の規則は文書に書いてあるだけで、守られる保証がない。
今回の仕事は、**Claude が新しいセッションで迷わず、間違えず、少ない読み込みで作業を始め、正しく終えて、次へ引き継げる状態**をつくることです。

### G1. 知識の構造化 (AI が読みやすいリポジトリ)
- 情報を種類ごとに分ける。種類は、現在の仕様・設計の理由・検証済みの結果・仮説・未解決の課題・経緯 (§4)。
  そのうえで、**1 つの情報の置き場所を 1 つ**にする。
  理由: 同じ情報が 2 か所にあると、片方だけが更新されて矛盾する。Claude はどちらが正しいかを判定できない。
- Claude が「どこを読めばよいか」を最短で判断できる入口と導線をつくる。
- 通常の作業で読む文書から、今の作業に要らない経緯を外す。ただし再現に必要な情報は失わない。

### G2. 規則が実際に守られるようにする (Claude Code の仕組みの活用)
- 規則ごとに、重要度と確実さに応じて置き場所を選ぶ。置き場所は、テスト / hooks / permissions / CLAUDE.md /
  `.claude/rules` / skills / subagents のいずれか。「文書には書いてあるが守られない」状態をなくす。
- 選び方は「破ったときの損害」と「機械で判定できるか」で決める (§5)。

### G3. 作業の型の定義 (プロジェクトの進め方)
- 開発の履歴 (文書・コミット・引き継ぎメモ) から、**繰り返し現れた手順と、繰り返した失敗**を抜き出す。
  それをもとに、次の 2 つを型にする。
  - 研究の 1 サイクル (仮説 → 実装 → 学習 → 評価 → 記録 → 判断)
  - セッションの始め方・終わり方・引き継ぎ方
- 型は、実際に繰り返されたものだけにする。想像で手順を増やさない。

### 成功の判定: cold-start テスト

「新しいセッションの Claude が、少ない読み込みで正しく答えられるか」を数字で測る。

**質問を作る (Phase 1)**
- 12〜15 問作る。種類を混ぜる: 現在の仕様 / 手順 / 制約とその理由 / 実験の再現 / プロジェクトの現在地。
- **リポジトリに答えがない質問を 2 問以上**入れる。正答は「記録がない・未確認」とする。
  推測で埋めずに「分からない」と答えられるかを測るため。

**正答を保存する**
- 【必須】正答と根拠 (ファイル:行) は**リポジトリの外**に保存する。場所は Phase 0 で決める。
  理由: リポジトリの中に置くと、回答役が grep で正答を見つけてしまい、測定が無効になる。
  質問文だけは `refactor/` に置いてよい。

**答えさせる**
- 回答役は general-purpose subagent とする。全問を 1 体に答えさせる試行を 2 回行い、ばらつきを見る。
- 回答役には次のように指示する。
  - `refactor/` と正答の保存場所を読まない。
  - 各回答に根拠のファイル:行を付ける。
  - 読んだファイルと行の範囲を列挙する。
- 読んだ量は、回答役の自己申告に加えて、結果に出るツール呼び出し数やトークン数を記録する。
- Phase 5 では CLAUDE.md が自動で読み込まれる。その行数も読んだ量に含める。
- auto memory などの、リポジトリの外の文脈が回答役に渡るかどうかを Phase 0 で調べ、測定の条件として記録する。

**採点する**
- 採点は、正答を持つ別の subagent が行う。区分は 正答 / 部分正答 / 誤答 / 根拠なしの正答 の 4 つ。
- 採点の基準は、回答を見る前に決めておく。

**比べる (Phase 5)**
- Phase 5 で同じテストを行う。それに加えて、**私が用意する未公開の質問 3〜5 問**も使う。Phase 5 の開始時に私へ依頼すること。
  理由: 文書が、決まった質問にだけ答えやすく作られてしまうのを防ぐため。

**達成の基準**
- 正答率が上がる。
- 読んだ量が減る。
- 未公開の質問でも、基準値と同等かそれ以上の成績になる。

## 3. 承認の範囲

| 承認なしで行ってよい | 私の承認が必要 |
|---|---|
| ファイルを読む、調査する、subagent を使う | 次のフェーズへ進む |
| `refactor/` の中での書き込み | ファイルの削除、Python の識別子の改名 |
| 作業ブランチへのコミット (小さな単位で) | `.claude/settings.json` の permissions・hooks の追加と変更 |
| 承認済みの提案の範囲内での文書の編集 | Isaac Sim や GPU を使うジョブの起動 |
| 不変条件を確かめるテストの追加 | 承認済みの提案からの大きな逸脱 |

その他の決まり:
- 【必須】push しない。
- 【必須】ユーザー設定 (`~/.claude/`) を変更しない。必要なら提案だけする。
- 【必須】自分が起動していないプロセスを kill しない。止める必要があれば、PID を私に伝える。

判断に迷うときの扱い:
- 上の表で判断できないときは、まず次の 2 点を考える。
  - 取り消しやすいか
  - 他の人の作業 (走っているジョブ、未コミットの変更) に影響するか
- 取り消しやすく、他に影響しないものは、自分で判断して `refactor/PROGRESS.md` に記録する。
- それ以外は止めて質問する。質問は、選択肢・推奨・推奨の理由の形にする。

## 4. 進め方: フェーズとゲート

### 共通の規約

**状態の記録**
- `refactor/PROGRESS.md` を常に最新に保つ。コンテキストが圧縮・リセットされても、
  `BRIEF.md` と `PROGRESS.md` を読めば再開できるようにする。書く項目は次のとおり。
  - 現在のフェーズ
  - 終わった項目
  - 次の 1 手
  - **承認済みの判断** (日付・内容・私の回答)
  - **未解決の質問**
- 圧縮の後、作業を再開する前に、必ずこの 2 つのファイルを読み直す。

**計画の書き出し**
- 各フェーズの最初に、計画を `PROGRESS.md` に書き出す。中身は、やること・順番・不確かな点・不確かな点の確かめ方。

**ゲートでの報告**
- 各フェーズの終わりに、成果物をファイルに書き出す。
- 報告は 20 行程度に収める。中身は、要点・私が判断すべき点・成果物のパス。詳細はファイルに書く。

**報告の根拠**
- 【必須】「完了した」「通った」と報告するときは、実行したコマンドとその出力 (要約でよい) を添える。
  実行していない検証を、済んだと書かない。

**作業ディレクトリの後始末**
- 作業ディレクトリは、最後に削除するか `docs/history/` へ移す。どちらにするかは Phase 5 で私が決める。

### Phase 0: 準備 (`refactor/` の外は編集しない)

1. **現状を確認する。**
   - `git status` を見て、未コミットの変更の扱いを私に確認する。選択肢は「先にコミットする」「別ブランチに残す」など。
   - `nvidia-smi` と `ps` で、走っているジョブを確認して記録する。触らない。
   - rope study が進行中かどうかを私に確認する。進行中なら、その文書は、再構成の範囲を Phase 2 で個別に決める。
2. **作業ブランチを切る** (例: `refactor/claude-foundation`)。
   `refactor/` の場所と、cold-start テストの正答の保存場所 (リポジトリの外) を提案する。
3. **Claude Code の現行の仕様を確認する。**
   claude-code-guide subagent か公式ドキュメントで確かめる。記憶の中の仕様を前提にしない。
   理由: 仕様は頻繁に変わる。誤った前提で設計すると、作った仕組みが黙って動かない。
   確かめる項目:
   - CLAUDE.md の読み込み規則 (ルート、サブディレクトリ、`@` import)
     - いつ読み込まれるか
     - import した文書は毎回全文が読み込まれるか
   - `.claude/rules/` (パスを限定した規則)
   - skills
     - frontmatter
     - 本文が読み込まれる時期
     - description が自動の呼び出しにどう効くか
     - subagent から使えるか
   - subagents の定義 (使えるツールの制限、モデルの指定)
   - hooks
     - イベントの種類
     - 入力の JSON
     - 終了コードの意味 (どの値で操作を拒否するか)
     - 設定の変更がいつ有効になるか
   - `settings.json` と `settings.local.json` の役割分担と優先順位
   - permissions の書式 (Bash のパターン、Read と Edit のパスの指定)
   - auto memory と、subagent に渡る文脈 (cold-start テストの条件に関わる)

   確かめた仕様は、出典を付けて `refactor/claude-code-spec.md` に要約する。Phase 2 の設計の根拠になる。

### Phase 1: 調査 (`refactor/` の外は編集しない。成果物は `refactor/audit/`)

**調査の進め方**
- 調査は範囲ごとに subagent に並列で任せ、メインのコンテキストを節約する。
- 各 subagent には、結果を `refactor/audit/<A〜G>.md` に書かせる。メインに返させるのは、要約 (結論と根拠のファイル:行) だけにする。
  Explore はファイルを書けないので、書かせる場合は general-purpose を使う。
- 【必須】各報告から 3 か所以上の根拠を、自分で開いて確かめる。誤りが見つかった報告は、全体を疑って確かめ直す。
- 順番の目安: C (用語) を先に終える。他の調査の結果を書くときに、用語が揺れないようにするため。

#### A. 文書の棚卸し
- 対象:
  - `.venv`・`.pytest_cache` を除く全 Markdown
  - 主要な docstring とコメント
  - `paper/` の文書
- 文書ごとに表にする項目:
  - ファイル
  - 行数
  - 現在の役割
  - 含まれる情報の種類 (§5 の分類)
  - 他の文書との重複・矛盾
  - AI にとっての問題
  - 推奨する移動先または分割先

#### B. 情報の分類
- 既存の記述を §5 の分類に振り分ける。
- Historical context と Obsolete information は、通常の作業で読む文書から外す候補として示す。

#### C. 用語監査
- 用語ごとに表にする項目:
  - 現在の表記
  - 意味 (複数あれば全部)
  - コード上の識別子
  - 推奨する正式名称
  - 互換名として残す必要 (タスク ID、ログ、チェックポイント)
- 重点的に確認する用語:
  - Twist、Knot: プリセット名とタスク ID の接頭辞 / knot_tying / 固結び (overhand knot) が衝突している
  - Simple、Stiff、Fine
  - Art28 系、Xpbd 系、Fem
  - LowMu
  - stage / 段
  - topology class
  - p-data
  - archive: 状態アーカイブと、文書の archive フォルダが衝突する
  - chain 評価
  - gate (ゲート 1)
  - 発散 / divergence
  - 1 手 / action / RL step
  - version: vN と pyproject の version
  - experiment / experiment_name
  - preset
  - backend / rope_backends
  - rope_model / rope study の「モデル」
  - next edge / ρ(g)
  - R2 除去

#### D. 規則と失敗の抽出
- 文書・HANDOFF・next_action・コミットの履歴から、次の 2 つを一覧にする。
  - 明文化された規則
  - 実際に起きた失敗・罠 (例: 整形報酬の検証の罠、出力のバッファリング、kill の拒否、FEM の固まり、
    `model_99.pt` が最後のチェックポイントであること)
- 各項目に付けるもの:
  - 出典 (ファイル:行、または commit)
  - 発生回数。数え方も書く (例: HANDOFF の何件の記録に現れたか)
  - 機械で判定できるか

#### E. 繰り返し現れた手順の抽出
- 次の手順が実際に何回行われたかを数え、手順 (コマンドを含む) を抜き出す。
  - バージョンの追加
  - 学習 → chain 評価 (複数 seed)
  - ゲート 1 (台本で結べるかの確認)
  - 発散の計測
  - 評価キューの実行と集計
  - 結果報告書の作成
  - セッションの引き継ぎ
- 記録が見つからないものは、回数を「記録なし」とする。推測で回数を埋めない。

#### F. コード構造の監査
- 次の候補を挙げる。挙動を変える変更は、まだ提案に留める。
  - 大きなファイル (例: `xpbd_rod.py` 1093 行、`overhand_script.py` 893 行)
  - 役割が曖昧なモジュール
  - 置き場所が不自然なもの (例: `knot_tying/outputs/`、`rope_study/` に混在するシェルスクリプトと報告書)
  - モジュール docstring の欠落
  - 重複した実装
  - lint の現状 (§2): ruff の指摘の内訳と、未整形のファイルの一覧

#### G. cold-start テストの基準値
- §1 の手順で行う。
- 質問は §9 の例を参考に、このリポジトリに合わせて作り直す。

**完了の条件**
- A〜G の成果物がある。
- 根拠の確かめを済ませ、その結果を各ファイルに記録してある。

**1. 情報の置き場所の表 (§5)**

**2. 文書の構成案** 【叩き台】

   docs/
     README.md               # 文書の地図と、読む順番
     glossary.md             # 用語と互換名の表
     STATUS.md               # 現在地・走っているジョブ・次の作業 (上書きで更新。追記しない)
     workflow.md             # 研究サイクルとセッションの規約 (人間向けの説明。手順の本体は skills)

  理由: 移動のたびに、リンク・人間の記憶・過去のセッションの記録が古くなる。

**3. 用語の正式名称と命名規則**
- 構造化した名前を検討する。軸は、表現 (Art / Xpbd / Fem)・分解能 (28 / 56)・摩擦 (nominal / LowMu)・剛性・用途。

  - 変更対象
  - 参照箇所の数 (grep の結果)
  - ログ・チェックポイント・タスク ID への影響
  - 後方互換の方法 (別名での登録など)
  - 文書だけでは解決できない理由

**4. Claude 基盤の設計 (§6)**

- hook には、さらに次を書く。
  - 誤検知したときの影響
  - 止める方法

**5. 作業の型 (§7) の案**

**6. コード構造の変更案 (Phase 4 の候補)**
- 各案に、リスク (高 / 中 / 低)、挙動が変わらないことの確かめ方、必要な工数を付ける。

**私が判断すべき点**

  - 文書の言語

    - hook では check だけ行う

### Phase 3: 文書と Claude 基盤の実装 (挙動を変えない)

**進め方**
- 承認された提案だけを実施する。
- 小さなコミットの単位で進める。コミットメッセージは既存の様式 (日本語・内容の要約) に合わせる。
- 実施の順番の目安:
  1. glossary
  2. system / decisions / experiments / history
  3. STATUS
  4. CLAUDE.md と rules
  5. skills / agents
  6. hooks と settings

  CLAUDE.md は、指す先の文書が揃ってから書く。
- ファイルの移動は `git mv` で行い、履歴を保つ。

**情報を失っていないことの確かめ方** 【必須】
1. 文書を移動・分割・要約・削除する前に、元の文書から次を機械的に抜き出し、一覧にして保存する。
   - commit のハッシュ
   - seed
   - iteration
   - チェックポイント名 (`model_*.pt`)
   - `logs/` などのパス
   - 単位の付いた数値と、% の数値
2. 作業の後、各項目が新しい文書のどこかに残っていることを、スクリプトで確かめる。
3. 消えた項目は一覧にして、意図した削除かどうかを報告する。

理由: 要約を繰り返すと、数値や条件が少しずつ抜け落ちる。自分では気づきにくい。

**Python の変更**
- コメントと docstring に限る。
- 不変条件を確かめるテストの追加は許可する。例: `common/topology` が isaaclab を import していないことを検査するテスト。
- 既存のテストを弱めない。
- 【必須】`logs/`・`outputs/`・チェックポイントは一切変更しない。

**hooks を有効にする前の確認**
- 想定する入力の JSON をスクリプトに渡して試す。
- 「拒否されるべき操作」と「通るべき操作」の両方を試す。

**skills の description の確認**
- 「呼ばれるべき依頼」3 つと「呼ばれるべきでない依頼」2 つを書き出す。
- description を読んで、それらを正しく区別できるかを確かめる。

### Phase 4: コード構造 (承認された項目だけ)

- 1 項目ずつ、変更 → 検証 → コミットの順で進める。
- 挙動が変わらないことを、可能な範囲で機械的に確かめる。
  - 登録されたタスク ID の一覧を、変更の前後で diff する。
  - 環境設定と PPO 設定のダンプを、変更の前後で diff する。
  - テストと ruff を通す。
- Isaac Sim を起動する検証は、GPU の使用状況 (`nvidia-smi`) を確認し、私の了承を得てから行う。
- 長時間ジョブの起動ラッパー (§6) もここで実装する。

- cold-start テストを再実行し、Phase 1 の結果と比べる。未公開の質問を含める (§1)。
- テスト、ruff、リンクの検査を行う。
  リンクは、全 Markdown の相対リンクが実在するファイルを指すことを、スクリプトで確かめる。
- §10 の最終報告を出す。

## 5. 情報の分類

| 分類 | 意味 | 置き場所の原則 |
|---|---|---|
| Current specification | 現在の実装の仕様 | 現在形で書く。コードの近く、または `docs/system/` |
| Design rationale | 現在も有効な設計の理由 | 局所的なものは docstring、横断的なものは `docs/decisions/` |

| Historical context | 過去の経緯 | `docs/history/`。通常は読まない |
| Obsolete information | 今は要らない情報 | 削除の候補。再現に必要なら `history/` へ |

## 6. 規則の置き場所の原則 (G2)

規則ごとに「破ったときの損害」と「機械で判定できるか」を見て、次の順で置き場所を選ぶ。
**上の段で強制できるものを、下の段に書いて済ませない。**
理由: CLAUDE.md に書いた規則は、文脈が長くなると守られないことがある。テストと hook は必ず実行される。

1. **テスト / CI**: 機械で判定できる不変条件。例: import の禁止、タスク ID の一覧、`mdp` の名前。
2. **hooks**: Claude が操作するたびに必ず実行したいもの。例: 編集後の lint、保護されたパスの編集の拒否。
   - 決定的に動く代わりに、作業を止めることがある。誤検知のコストも考える。
   - hook が介入できるのは Claude のツール呼び出しだけである。学習スクリプトがログを書くことは妨げない。
3. **permissions** (`.claude/settings.json`): 許可・確認・拒否するコマンドとパス。
   - チームで共有するものは `settings.json`、個人のものは `settings.local.json` に置く。
   - kill・pkill は allow に入れない。
   - 対象外の旧実装のディレクトリを読まないための設定を検討する。
     ただし、そのディレクトリがユーザー設定で追加されている場合は、提案に留める。
4. **CLAUDE.md** (ルート): 毎セッション必要で、機械では判定できない規則と、入口への導線。
   - 目安は 150 行以内。
   - 各行が「消すと Claude が間違えるか」の試験に通ること。
   - README と重複させない。
   - `@` import で大きな文書を取り込まない (Phase 0 で確かめた仕様に照らして判断する)。
5. **パスを限定した規則** (`.claude/rules/` や、サブディレクトリの CLAUDE.md): 特定のディレクトリで作業するときだけ要る規則。
   例: `common/topology/` の import 禁止の理由、`versions/` の追加の規約。
6. **skills** (`.claude/skills/`): 手順。本文は呼ばれたときだけ読み込まれるので、長い手順はここに置く。
   description は「いつ使うか」を判断できる具体的な書き方にする。
7. **subagents** (`.claude/agents/`): 大量のログや文書を読む作業を、メインのコンテキストから隔離するためのもの。
   例: ログと結果の分析、文書の整合性の監査。
8. **auto memory**: 個人の好みや、セッションをまたぐ一時的な知識。リポジトリが持つべき事実はここに置かない。

## 8. 作業の型 (G3)

Phase 1-D / E の根拠をもとに、次の 4 つを定義する。

### 1. 研究の 1 サイクル
- 流れ: 仮説 → (必要なら) 新しいバージョンや設定 → ゲート (学習前の確認) → 学習 → 評価 → 実験記録 → 判断 →
  STATUS と decisions の更新
- 各段階に、終了の条件と残す記録を書く。
- 既存の知見を反映する。例:
  - seed 間の差が 15〜19 ポイントあるので、2 seed 以上で比較する。
  - 学習の前にゲート 1 を通す。
- 否定的な結果も、実験記録として残す。

### 2. 実験記録のテンプレート
次の項目を持たせる。
- 目的と仮説
- commit
- タスク ID とプリセット
- 変えた変数
- seed
- iteration
- num_envs
- 学習と評価のコマンド
- ログとチェックポイントのパス
- 指標
- 結果 (表)
- 結論: 「分かった / 推測 / 未確認」を区別する
- 次の作業

### 3. セッションの規約
- 始め: STATUS を読む、git status を見る、走っているジョブを確認する。
- 終わり: STATUS を上書きで更新する、実験記録を書く、コミットできる状態かを確認する。
- 引き継ぎメモを追記で長くしていく形 (今の HANDOFF.md の形) をやめる。代わりに次の 2 つに分ける。
  - 上書きで最新を保つ STATUS
  - 一度書いたら変えない実験記録

### 4. 長時間ジョブの規約
- 起動の方法
- 記録の場所
- 止め方: 自分が起動していないプロセスは kill せず、PID を人間に伝える。
- GPU の共有

## 9. 書き方の規則

**仕様の書き方**
- 現在の仕様は現在形で書き、経緯を本文に混ぜない。
  「以前は X だったが Y に変えた」ではなく、「Y は … である」と書く。
- 過去の名前は、glossary の互換表 (タスク ID、ログのディレクトリ、チェックポイント、過去の実験名) にだけ置く。

**文書の構成**
- 1 つの文書の主な目的は 1 つにする。
- 冒頭の 1〜2 文に「この文書を読むべき状況」を書く。
- 長い文書には目次を付ける。

**数値と確かさ**
- 数値には単位を付ける。
- 結果には、条件・seed・iteration・評価の方法を併記する。
- 「分かった / 推測 / 未確認」を明示する。
- 書き直しや要約のときに、数値や条件を落とさない (§4 Phase 3 の確かめ方を使う)。

**リンク**
- Markdown のリンクは、実在するファイルだけを指す。

**docstring**
- 日本語で書く。
- 「何をするか」より「なぜそうしたか (今も有効な理由)」を書く (既存の規則を踏襲)。
- 経緯は書かない。必要なら decisions へリンクする。

**読み手**
- AI 向けの文書でも人間が読む。表と短い段落を基本にし、要点を先に書く。

**cold-start テストの質問の例** 【叩き台】 (Phase 1 で、このリポジトリに合わせて作り直す)
- v6 の chain 評価を seed 43 で再現するには、どのコマンドとチェックポイントを使うか。
- `Knot` プリセットの物理パラメータは、どこで定義されているか。他のプリセットとの違いは何か。
- `common/topology/` で isaaclab を import してはいけない理由は何か。破るとどうなるか。
- 新しいバージョン v8 を追加する手順は何か。
- rope study で次にやるべき作業の 1 番目は何か。その理由は何か。
- `common/mdp/` の既存の報酬項の挙動を変えたいときは、どうすべきか。
- `Art28` と `XpbdC28` の違いは何か。それぞれのログはどこにあるか。

## 11. あなた (Claude) が陥りやすい失敗と、その対策

この種の作業で起きやすい失敗を挙げる。各フェーズの終わりに、自分の作業がこれに当たっていないかを確かめること。

| 失敗 | 対策 |
|---|---|
| 根拠のない skill・規則・文書を「あると便利そう」で作る | 各ファイルに Phase 1 の根拠の番号を付ける。付けられないものは作らない |
| 要約や書き直しで、数値・条件・注意書きを落とす | Phase 3 の、抜き出した一覧との照合 |
| subagent の報告を確かめずに、文書へ書き写す | 根拠のファイル:行を自分で開く |
| 前提が違うと気づいても、計画どおりに進める | 止めて PROGRESS.md に記録し、報告する |
| 実行していない検証を「確認済み」と書く | コマンドと出力を報告に添える |
| 圧縮の後、承認されていない判断を「承認済み」と思い込む | PROGRESS.md の「承認済みの判断」だけを承認として扱う |
| 文書を cold-start テストの質問に合わせて最適化する | 未公開の質問で確かめる。文書は一般的な作業のために書く |
