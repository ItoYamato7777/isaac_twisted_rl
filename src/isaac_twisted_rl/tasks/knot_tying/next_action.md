## 1. 完了済み (Step 1〜3): `topology/` パッケージ

ロープの 3D 点列から p-data を作る **純粋ロジック層**。検証済み。

```
topology/
├── __init__.py            公開 API
├── representation.py      Point / Edge / Face / AbstractState (半辺構造と p-data)
├── intersections.py       バッチ化 2D 自己交差検出 (テンソル層)
├── state_2_topology.py    交差 -> AbstractState -> p-data (記号層)
└── polyline.py            ポリライン前処理 (節点生成・中心寄せ・細分・再標本化)
```

### 使い方

```python
import torch
from isaac_twisted_rl.tasks.knot_tying import topology as tp

# (num_envs, num_links, 3) のリンク中心 -> (num_envs, num_links+1, 3) のポリライン
nodes = tp.polyline_from_link_centers(link_pos)

# テンソル層: バッチ / GPU。4096 環境で 1.6 ms
batch = tp.segment_intersections(nodes)
batch.count      # (num_envs,)          交差数
batch.writhe     # (num_envs,)          符号の総和
batch.data       # (num_envs, M, 4)     (seg_i, seg_j, over, sign)
batch.order      # (num_envs, M, 2)     交点の出現順 (1 始まり)

# 記号層: env ごとの Python。4096 環境で 94 ms。呼ぶ頻度を絞ること
p_datas = tp.p_data_from_batch(batch, short=True)   # ['1U2+_2O1+', ...]

# 可視化用: 交差の xy 座標を復元 (Step 5 で追加)
xy = tp.crossing_positions(nodes, batch)            # (num_envs, M, 2), 無効は NaN
```

### 検証済みであること

- **原実装との一致**: ランダムなポリライン 600 本で twisted_rl の
  `state2topology` と突き合わせ、**全件一致**。
  (原実装の `find_new_intersections` にある「細分の反復で `num_of_points` が
  更新されず折れ線の末尾が切り落とされる」バグを直したうえでの比較。
  未修正の原実装とは 600 本中 32 本で食い違うが、すべて原実装側の欠陥)
- **単体テスト 69 件**。Isaac Sim 不要で走る (実行方法は「5. 作業上の約束」参照)
- 三葉結びが離散化解像度 (40〜200 節点) に依らず交差 3 つ / writhe -3 を返す
- 平行移動・z 軸回転・一様スケールで p-data が不変
- float32 (Isaac Lab の既定 dtype) でも float64 と同じ p-data
- **動いている物理の上でも正しい** (Step 5 で目視検証。下記 3 節)

### 移植元から意図的に変えた点 (レビュー時に把握しておくこと)

1. **shapely を使わない。** 線分交差は解析解。`alpha` / `beta` が直接出るので
   原実装のような距離比からの逆算が要らない。
2. **セグメント細分を廃止。** 原実装は「1 セグメントに交差 2 つ」を扱えず、
   セグメントを細かく割って回避していた。本実装は交差の弧長パラメータ
   `seg + alpha` を直接ソートして出現順を決めるので細分が不要。
   これで環境ごとに長さの変わる逐次ループが消え、**4096 環境で 2735 ms →
   1.6 ms** になった。正しさも失われていない (上記の一致検証)。
3. **面の再構築の走査上限**を定数 10 から辺の総数に変更。原実装は交差が
   3 つ以上あると面をたどり切れなかった。
4. メソッド名 `addPoint` / `removePoint` は移植元の camelCase のまま。
   将来 `cross` / `Reide1` / `Reide2` をコピーしてくるときの事故を防ぐため。

### 分かったこと (Step 6 に効くので必ず読むこと)

**(a) 位相抽出は動く物理の上でも正しい。これが Step 5 の主目的で、達成済み。**
グリッパーが持ち上げた端が本体をまたぐと `crossings=1 /
p_data='1O2+_2U1+'` が出る。図で z の色 (明るいほど上) と注記の O/U を
突き合わせ、上下判定・符号・交点番号がすべて期待どおりであることを確認した。
**Step 1〜4 は実機入力でも通る。**

**交差を「手を離しても残る」状態にする問題は解決済み** (下記 (c))。

**(b) 交差を作るには「たるみ」が要る。Step 6 の行動設計に直結する。**
真っ直ぐなロープでは、掴んだ点 G からロープ上の点 K までの弧長は直線距離に
等しい。一方ハンドが G から K の向こうへ回り込む経路は必ずそれより長いので、
経路長が弧長を超えた瞬間にロープが張り切り、**端だけが本体を渡るのではなく
ロープ全体が平行移動する**。

そのため台本は 2 段構えにしてある: 1 手目でロープを大きく曲げてたるみを稼ぎ、
2 手目でそのたるみの範囲内で端を本体の上に渡す。渡し先は絶対座標ではなく
**リンク K の現在位置から実行時に決める** (`GraspMove.over_link_frac`)。
1 手目の結果は物理次第で毎回違うため、決め打ちでは本体を越えられない。

**(c) 「離したのに付いてくる」問題は物理パラメータで解決した (解決済み)。**
当初、指を開いて真上へ退避するとロープが指に残ったまま持ち上がり、作った
交差が壊れていた。対策は 2 つで、どちらもコードに反映済み:

| 対策             | 場所                                      | 内容                                                                                                                                                                 |
| ---------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ロープを柔らかく | `rope_specs.py` の `TWIST_YOUNGS_MODULUS` | `twist` のヤング率だけ 1.0e6 → **1.0e5 Pa** (1/10)。曲げ剛性 EI はヤング率に比例するので曲げ関節のばね定数も 1/10 になり、指を開いたときにロープの腰で引っかからない |
| 指を常に全開に   | `topology_debug_demo.py` の `OPEN_RATIO`  | 0.8 → **1.0**。接近時も離すときも全開                                                                                                                                |

`twist` だけヤング率を下げたのは、**グリッパーで挟んで運ぶ用途に特化した
プリセット**にしたため。`stiff` / `fine` は比較用に `ROPE_YOUNGS_MODULUS`
(1.0e6) のまま残してある。角度制限・質量など幾何や慣性由来の量は変えて
いないので、位相抽出側への影響は無い。

→ **学習に使うプリセットは `twist`。** 他のプリセットに切り替えるときは、
この「離すと付いてくる」現象が再発しないか必ず確認すること。

なお `RELEASE_RATIO` (1.0) の docstring は「接近時の `OPEN_RATIO` より
広く開ける」と書いてあるが、`OPEN_RATIO` も 1.0 になったので現在は同値。
実害は無いが記述と実態がずれている。

### 4.1 アクション空間: ロープ相対 + `Δlink` (決定)

```
grasp_link_id  離散 {2, ..., N-3}     掴むリンク
delta_link     離散 {-8, ..., +8}     → target_link_id = clip(grasp_link_id + delta_link, 0, N-1)
drop_x_rel     連続 ±0.15 L           target_link の現在位置からの xy 変位 (L=ロープ全長)
drop_y_rel     連続 ±0.15 L
drop_z_rel     連続 0 〜 3 ロープ直径  置くときの高さ (把持高さからの上乗せ)
end_yaw        連続 ±π                置き終わりの手首 yaw
```

計 7 次元 (離散 2 + 連続 4)。`via_*` (中間経由点) は**最初は入れない**。

#### なぜ「置く先」を絶対座標にせず、リンク相対にするのか

これが Step 6 の設計で一番重要な判断なので、根拠を全部書いておく。

1. **人間が設計した最良の手順ですらリンク相対でしか書けなかった。**
   Step 5 の台本の 2 手目は `over_link_frac` (= 渡し先をリンク K の現在位置
   から実行時に決める) を使っている。1 手目でロープをどう曲げるかは物理次第で
   毎回違うため、絶対座標の決め打ちでは本体を越えられなかった
   (`topology_debug_demo.py` の `GraspMove.over_link_frac` docstring)。
   これが一番強い経験的根拠。

2. **pick&place 粒度では、離した瞬間にロープが物理で動く。**
   次のアクションを決める時点でリンク位置は前回と違う。置き場所を絶対座標で
   持つ意味がほぼ無い。

3. **絶対座標にすると「微小操作」の学習が逆に難しくなる。**
   「リンク i を 2 cm 右へ動かす」という同じ意図が、リンク i の現在位置に
   よって毎回違う出力値になる。エージェントは観測からリンク位置を読み取って
   引き算する関数を学ばねばならず、その答えは毎ステップ変わる。
   リンク相対ならこの引き算が座標系のレベルで埋め込まれる
   (object-centric action space。方策が並進不変になりサンプル効率が上がる)。

4. **キネマティックハンドなので、絶対座標を使う利点が無い。**
   IK 失敗も可達領域外も無いため、リンク相対で指定した位置には必ず行ける。
   「絶対座標のほうが実機の可達領域を直接扱える」という利点が消える。

#### なぜ `target_link_id` そのものではなく `Δlink` にするのか

**探索空間と意味の一貫性**のため。

- `grasp_link_id` と `target_link_id` を独立に選ばせると N×N (20 リンクなら
  400 通り) の離散ペアになる。`Δlink` なら 20×17。
- `Δlink` は「隣を掴む」「8 個先を狙う」という**状況に依らない意味**を持つので
  方策が汎化しやすい。`target_link_id=10` の意味は `grasp_link_id` が
  3 か 15 かで全く変わってしまう。

#### 「1 アクションで必ず位相が変わってしまうのでは」への回答

検討時に「`target_link_id` があると 1 アクション = 1 トポロジー変化に固定
されて、少しずつ紐を操作する戦略が表現できないのでは」という懸念が出た。
結論は **`target_link_id` が原因ではなく、`drop_*_rel` の許容範囲と
`Δlink=0` を許すかどうかで決まる**。上記の設計では:

- `delta_link = 0` → 掴んだリンクのすぐ近くに置き直す = **微調整モード**
- `delta_link = ±8` → 本体の向こう側へ渡す = **位相を変えるモード**

どちらを使うかはエージェントが選ぶ。表現力は絶対座標版より**広い**
(絶対座標では上記 3 の引き算が必要で、実質学習できない)。

さらに、行動粒度を「1 アクション = pick&place 全部」に決めたことで、
**「少しずつ操作する」はアクション内の微小変位ではなく、複数回の
pick&place として表現される**。Step 5 の台本がまさにこれ
(1 手目: たるみ作り / 2 手目: 渡す) で、1 エピソード 3〜5 アクションになる。

#### 検討したが採らなかった案

**案②「パラメトリック曲線生成」**
(`[grasp_link_id, target_link_id, approach_height, curve_radius, twist_yaw_angle]`)。
`approach_height` / `curve_radius` が「たるみを作る」ことを軌道の形として
直接パラメータ化しており、上記 3(b) の幾何と相性が良い。ただし:

- **始点・終点が決まらないと曲線が定義できないので、②も結局
  `grasp_link_id` と終点指定が要る。** `target_link_id` の要否とは直交する話。
- ②は①の `via_*` を曲線パラメータに圧縮した版と見なせる。

→ **まず①から `via_*` を落とした版で始め、動いてから `via_*` や②の
曲線パラメータを足す。** 理由は (1) Step 5 の台本は `path` (= `via_*` 相当) を
1 手目でしか使っておらず 2 手目は `over_link_frac` だけで成立している、
(2) 「たるみを作る」1 手目は `delta_link=0` + 大きめの `drop_xy_rel` で
表現できる、(3) 次元が少ないほうが学習が速い。

#### 端リンクを除外する理由

`grasp_link_id` の範囲を `{2, ..., N-3}` としているのは、端ちょうどを掴むと
接触面積が足りず滑るため (`topology_debug_demo.py` の `grasp_move` で
`max(2, min(link_id, num_bodies - 3))` としているのと同じ)。
`target_link_id` 側は範囲を絞る必要が無いので `{0, ..., N-1}` に clip する。

### 4.2 最初の報酬 (交差 1 つを作って残す)

p-data は離散量なので、一致 / 不一致だけでは勾配が出ない。密報酬と併用する。

```
r_sparse   = +1.0  * (最終状態で crossings >= 1)     エピソード終端のみ
r_progress = +0.3  * Δcrossings                      アクションごと
r_shaping  = -0.05 * |grasp_point - hand_pos|        掴めたか (整形)
r_penalty  = -0.2  * (把持失敗 / NaN)
```

**最重要: `r_sparse` は必ずハンドを退避させた後に測ること。**
そうしないと「ハンドで吊って交差を見せかける」方策を学習する。3(c) の
物理パラメータで「離すと付いてくる」問題は解決したが、報酬の測定タイミングは
それとは別に明示的に押さえておく必要がある。台本の `park` フェーズ
(`PARK_XY = (0.0, -0.9)` へ退避 → `FINAL_SETTLE_TIME` 待つ) が
そのまま使える。

ログには `rope_zmax` と `finger_gap` を必ず出すこと。位相の変化を見るときは
この 2 つも一緒に見ないと、「ハンドが吊っているだけ」を「交差が残った」と
取り違える。

### 4.3 `knot_tying/mdp/` を作る

Isaac Lab の manager-based の作法に従う。参考: `../lift/mdp/`。

```
mdp/
├── __init__.py
├── observations.py    交差数 / writhe / 符号列 などテンソル層の量
├── actions.py         4.1 の行動空間 + pick&place のステートマシン
├── rewards.py         4.2 の報酬
└── terminations.py    目標トポロジー到達判定
```

**観測は p-data 文字列を使わないこと。** テンソル層 (`IntersectionBatch`) の
数値をそのまま流す。理由は `state_2_topology.py` の docstring の実測値を参照
(文字列生成は 4096 環境で 94 ms、テンソル層は 1.6 ms)。
`RopeTopologyExtractor` がこの使い分けをそのまま API にしてある。

p-data 文字列が要るのは報酬・終了判定・ログだけ。しかもそれらは毎ステップ
全環境で回す必要が無い (エピソード終端のみ、あるいは数ステップに 1 回)。

#### `actions.py` が Step 6 の実装の山場

`topology_debug_demo.py` の `grasp_move()` は「1 手」を
**逐次的に**実行している (`plan` の各フェーズを `run_segment` で順に回す)。
フェーズは以下の 13 個:

```
approach → descend → close → hold → lift → carry1..k
        → lower → release → settle_out → clear → retreat → relax
```

各フェーズの尺は `topology_debug_demo.py` の `APPROACH_TIME` 以下の定数群に
ある (合計およそ 11 s + carry。`CARRY_TIME` は経由点で等分)。

**RL では全環境が並列に別々のフェーズにいる**ので、これをそのまま使えない。
フェーズ ID と経過時間を `(num_envs,)` のテンソルで持つステートマシンに
書き換える必要がある。`grasp_move()` のロジック (掴む点の決定、渡し先の
実行時決定、`clear` の方向計算、`place_z` の計算) は関数として切り出せば
再利用できる。

1 アクションが約 11 s = sim_hz 240 なら **2600 物理ステップ**。
1 エピソード 3〜5 アクションで 8000〜13000 ステップになる。
学習の実時間はここで決まるので、フェーズの尺は詰められるだけ詰めること
(台本は目視デバッグ用に余裕を持たせてある)。

### 4.5 解決済み: NaN 対策 (実測値あり)

**結論: 240 Hz で回すこと。120 Hz にしてはいけない。**

`twist` / 16 環境 x 10 手 / ランダム方策での発散率の実測:

| 設定 | 発散率 |
|---|---|
| 120 Hz | 11.2% |
| **240 Hz** | **1.2%** <- 採用 |
| 240 Hz + `make_rope_physx_cfg` | 3.8% |

当初は学習の実時間を稼ぐため 120 Hz を試したが、把持中の接触でロープの
速度が 60〜175 m/s (正常時は 1 m/s 程度) まで跳ね上がり NaN になった。
原因は `rope_cfg.py` の `max_depenetration_velocity` が **240 Hz を前提に**
スケールされていること (`_SIM_HZ_REF = 240.0`)。120 Hz では 1 ステップの
押し戻し量が倍になり、「半径の 40% 以上は押し戻さない」という前提が崩れる。

`make_rope_physx_cfg` を併用すると却って悪化するのは、あれがシーン全体の
接触設定を変えてグリッパーの押し付け力にも影響するため
(`rope_cfg.py` の warning に明記されている)。

残った 1.2% は `terminations.rope_diverged` がその場で reset し、
`rewards.action_failed` が罰を与える経路で吸収している。

プリセット別 (240 Hz, ランダム方策 20 手): `twist` / `simple` / `stiff` は
発散 0、`fine` のみ 20 手あたり 1〜2 回。`fine` で本格的に学習を回すなら
さらに `sim.dt` を詰める必要がある。

## 4.8 Step 7: 固結び (overhand knot) への拡張 (2026-09-15 実装)

Step 6 の「交差 1 つ」から最終目標の **固結び (三葉結び、交差 3 つ)** へ
引き上げた。移植元の構成 (記号プランナ + 単一 Reidemeister スキル) は
**採らなかった**。理由と代わりの設計を残す。

### 4.8.1 なぜ移植元の構成をそのまま使わないか

移植元 TWISTED-RL は **結び目そのものを一度も報酬にしていない**。
報酬は `{+1 目標位相に一致 / -1 それ以外へ変化 / 0 不変}` の疎報酬で、
**位相が変わった瞬間にエピソード終了**。固結びは記号 BFS プランナが
単一移動スキルを 3 回連鎖させて組み立てる。

これを支えているのが **HER** と **replay buffer を次段の初期状態プールに
するカリキュラム** (G0→G1→G2)。どちらも **off-policy (SAC) 前提**で、
本リポジトリの on-policy PPO には載らない (PPO は更新ごとにデータを
捨てるので buffer も relabel も無い)。

→ 後述の報酬ラダーが **HER の機能的な代替**。HER の役割は「目標では
ないが何らかの位相に到達した」に学習信号を与えることで、ラダーはそれを
より密に、記録の手間ゼロで与える。

### 4.8.2 固結びはテンソル層だけで判定できる (この拡張の要)

移植元の BFS で **到達可能な 3 交差状態 528 個を全列挙**して調べた結果、
固結びは以下の 3 条件で厳密に特徴づけられる:

1. 交差数が 3
2. **partner gap が全て 3** (`|order[...,0] - order[...,1]| == 3`)
3. **符号が全て同じ** (`|writhe| == 3`)

528 個中この 3 条件を満たすのはちょうど 4 個で、固結びの p-data 4 通り
(キラリティ 2 × 走査方向 2) と完全に一致する。

**条件 2 だけでは足りない** (16 個残る)。**条件 3 だけでも足りない** —
独立した R1 ループ 3 つが `1U2+_2O1+_3U4+_4O3+_5U6+_6O5+` で同符号に
なってしまう。**両方必要**。

→ **94 ms の記号層を使わずに済む。** `cross` / `Reide1` / `Reide2` の
移植も不要になった (4.7 は引き続き「将来やるとしたら」の話)。

### 4.8.3 厳密な `交差数 == 3` は実機で使えない

三葉結びの尻尾に小さなループが 1 つ付くだけで交差数は 7 に増え、
gap は `[3,3,3]` から `[5,5,9,9,3,5,1]` へ **全ての点番号が振り直される**。
結び目は物理的に存在するのに厳密判定は何も見つけられない。20 リンクの
たるんだロープではこれは例外ではなく常態。

そこで **部分列 (subsequence) 判定**にした。「交差の k 個組のうち、
**その k 個だけで番号を振り直したとき** に gap が全て k かつ同符号に
なる組が存在するか」を見る。実測:

| 入力 | 交差数 | 判定 |
|---|---|---|
| 三葉結び (きれい) | 3 | True |
| 三葉結び + 尻尾ループ | 7 | **True** (厳密判定では False) |
| 結ばれていないコイル | 3 | False |
| ランダムロープ 600 本 | 0〜5 | 誤検出 **0 %** |

実装は `topology/knot_detect.py`。env ごとの Python ループを持たない
完全ベクトル化で、交差数の上限 8 で 3 個組は C(8,3)=56 通りの定数テンソル。

### 4.8.4 報酬は位相クラスのラダー + ポテンシャル整形

`crossing_progress` (Δ交差数) には **R1 を 3 回ひねれば交差数 3** という
抜け道があり、固結びには一歩も近づかない。そこで交差数ではなく
**位相クラス** を段にする:

| 段 | Φ | 位相 |
|---|---|---|
| 0 | 0.00 | 交差なし / 行き止まり (独立ツイストなど) |
| 1 | 0.35 | 交差 1 つ (**Step 6 の目標がそのまま 1 段目**) |
| 2 | 0.70 | 絡み 2 交差・同符号 |
| 3 | 1.00 | 固結び |

三葉結びを途中まで描くと段が 0 → 1 → 2 → 3 と順に上がることを確認済み
(`tests/test_knot_detect.py::test_partial_trefoil_walks_up_the_ladder`)。
ラダーは人間が結ぶ手順とそのまま対応している。

**ポテンシャル整形 `F = γΦ(s') − Φ(s)` にすること。**
`if class == 2: +0.70` のように段そのものに報酬を付けると、**2 段目に
居座って毎手ボーナスを稼ぐ**のが最適方策になる (このタスクで最も
起こりやすい報酬ハッキング)。ポテンシャル形式なら段に留まるだけでは
`γ·0.70 − 0.70 ≈ −0.014` にしかならず、しかも Ng et al. (1999) により
**最適方策を変えないことが保証されている**。

**`gamma` は PPO 側と必ず一致させること** (どちらも 0.98)。ずれると
この不変性が崩れる。`RewardsCfg.shaping.params["gamma"]` と
`KnotTyingPPORunnerCfg.algorithm.gamma` の両方にコメントを置いてある。

### 4.8.5 直したバグ: `first_crossing_feature` の正規化

旧実装は正規化の分母に `batch.data.shape[1]` (= **バッチごとに変わる**
最大交差数) を使っていた。docstring の「節点数で割る」とも食い違っており、
**同じロープでもバッチに何が入っているかで値が変わっていた**:

    同じ三葉結び 単独で       -> point_i/j = 0.333 / 1.333  (1 を超える)
    同じ三葉結び バッチ内で   -> point_i/j = 0.167 / 0.667

`empirical_normalization=False` のまま critic に分布シフトを注入していた。
`crossing_features` で置き換え、分母を `2 × 節点数` という定数にした
(全成分が `(0, 1]` に収まる)。旧関数は ablation 用に残してあるが
`ObservationsCfg` からは外れている。

### 4.8.8 整形報酬を検証するときの注意 (実際に踏んだ罠)

`knot_class_shaping` が正しいかを確かめるとき、**`env.step()` から
返ってきた後に位相クラスを読んではいけない**。2 つの理由で
「報酬が使った値」と違うものを見てしまう:

1. **reset のタイミング。** `ManagerBasedRLEnv.step()` は
   `termination -> reward -> _reset_idx -> observation` の順に処理する
   (`manager_based_rl_env.py`)。終了した env は報酬計算の後にロープが
   初期姿勢へ戻るので、step 後に読むと `Φ(s')` が reset 後の値になる。
2. **`_episode_sums` は reset でゼロクリアされる** (`reward_manager.py`
   の `reset()`)。エピソードをまたいで積算値を比較すると必ずずれる。

正しい検証方法は、報酬関数自体を差し替えて **報酬が計算されるその瞬間に**
`Φ(s)` と `Φ(s')` を捕まえること。実際にそうすると誤差は厳密に 0 になる。

素朴に step 後へ読んだ版では最大 0.455 のずれが出て、しかも終了した env が
無いステップでもずれた (抽出器が `common_step_counter` でスタンプされて
いるため、どのタイミングで呼ぶかで返る batch が変わる)。**報酬のバグでは
なく検証方法のバグ**だったが、気付きにくいのでここに残す。

### 4.8.10 ゲート 1 の結果 (2026-09-27): 台本で固結びは結べる

**結論: 通った。ただし `twist` では長さが足りず、新プリセット `knot` が要る。**
6 次元の行動空間で再生するには `drop_xy_rel_frac` の拡大とフェーズの尺の延長も要る。

検証スクリプトは `demos/overhand_script.py` (台本の中身と使い方は docstring)。
学習環境をそのまま `gym.make` し、ハンドだけを台本で動かす。128 環境で台本の
パラメータを ±25% 揺らし、ハンドを退避させてから **R2 除去後の位相** で判定した。

#### 台本 (5 手)

slack (たるみ) -> loop (輪。先端側が上) -> tail (先端を輪の外側へ) ->
**cover (輪の片側 edge A を掴んで尻尾の上に被せる)** -> tuck (先端を輪の反対側
edge B の上へ)。pick&place では掴んだ部分が必ず上になるので、固結びの「下」は
cover のように **輪の側を動かして** しか作れない (Report §5.4 の予想どおり)。

#### 成功率 (固結び / 128 環境)

| 条件 | `twist` (20 リンク) | `knot` (28 リンク) |
|---|---|---|
| 台本, 運搬高さを手ごとに調整, 7.8 s/手 | 23 (18%) | 77 (60%) |
| 台本, **運搬高さ 0.20 m 固定** (学習と同じ), 7.8 s/手 | 0 (`knot` 用の台本は移らない) | **122 (95%)**, 発散 0 |
| 同上, 3.2 s/手 (descend/lift/lower 0.3 s, carry 0.6 s) | — | **116 (91%)**, 発散 3 |
| 同上, 学習の尺 (v2 `SHORT_DURATIONS`, 2.44 s/手) | — | carry 0.35 s のままでは 1 手目で 13/32 が発散 |
| 6 次元行動で再生 (`env.step`), 7.8 s/手, `drop_xy` ±0.15 L | — | 36 (28%) |
| 同上, 3.2 s/手 | — | 12 (9%) |
| 6 次元行動で再生, 7.8 s/手, **`drop_xy` ±0.30 L** | — | 54 (42%), 発散 19 |
| 同上, 3.2 s/手 | — | **84 (66%)**, 発散 9, クリップ 0 (1 手目を除く) |

#### 分かったこと

1. **長さが決め手。** 固結びは本体 ~8 / 輪 ~12 / 尻尾 ~8 リンクを使う。20 リンクの
   `twist` では tuck の時点で輪の中の尻尾が 2〜3 リンクしか残らず、持ち上げると
   edge A の下から抜けて C1 に戻る。`knot` は `twist` と材料・太さを同じにして
   28 リンクに延ばしただけ (1 リンクの物理が同じなので把持・「離すと付いてくる」
   対策・発散しにくさをそのまま引き継ぐ)。根拠は `rope_specs.KNOT_NUM_LINKS`。
2. **運搬高さ 0.20 m 固定は障害ではない (むしろ良い)。** 被せる手・通す手を低く
   運ぶ台本 (60%) より、全部 0.20 m の台本 (95%) のほうが成功した。Report §5.6 /
   P3-1 の「z_max を行動に入れる」は、少なくとも固結びには不要。
3. **`drop_xy_rel_frac` = 0.15 は足りない (next_action.md 4.8.9 の予想どおり)。**
   cover の置き先は 128 環境中 79〜97 で target リンク ±8 本 + ±0.15 L の外にあり、
   クリップされて輪ごと崩れた。0.30 に広げた結果は上の表。
4. **`knot` は学習の短い尺で発散する。** 原因は運搬速度 (carry 0.35 s で 0.5 m 以上、
   1.14 m の本体を引きずる)。carry 0.6 s で 1 手目の発散は 13/32 -> 0/32。
   ソルバ反復 32・指ゲイン 2 倍は効かなかった。descend が速いと、結び目の上へ
   指を降ろす手でも発散する (tuck の descend/close で 18/128)。
5. **R2 版のラダーは cover の手を評価できない。** cover の直後は多くの場合
   edge A のたるみが尻尾を 2 回またいだ `1U4+_2O5+_3O6-_4O1+_5U2+_6U3-` で、
   R2 除去すると C1 (`1U2+_2O1+`) と同じになる。しかしこの状態から tuck で
   約 7 割が固結びになる (本物の C2 `1U3+_2O4+_3O1+_4U2+` を経由するのは成功の
   一部だけ)。v2-R2 の報酬では「cover を打っても何も起きていない」ように見えるので、
   Report P1-3 の BFS 距離ポテンシャルなど、この状態を段として数える設計が要る。
6. 台本の途中状態 (輪 / cover 後 / C2) は、Report P1-1 の「到達状態アーカイブ
   からのリセット」の初期アーカイブにそのまま使える。
7. **6 次元の行動空間でも結べる (66%)。** 条件は `drop_xy_rel_frac` 0.30 と
   3.2 s/手の尺 (descend/lift/lower 0.3 s, carry 0.6 s)。1 手目 (たるみ) の置き先は
   ±0.30 L でも届かずクリップされるが、クリップ後の形でも後続は成立する
   (届く範囲に台本を直すと 49/128 に下がった)。
   * 共有層の既定値 (`GraspLimits` / `SHORT_DURATIONS`) は変えていない。v0〜v2-R2 の
     挙動を変えないため (README の規約 3)。学習に使うなら新バージョン (v3) で
     `Knot` プリセット・`drop_xy_rel_frac=0.30`・上の尺を配線すること。
   * **未解明:** 同じ尺でも `env.step()` で再生すると台本モードより発散が多い
     (3.2 s/手で 9 vs 3、7.8 s/手で 19 vs 0)。遅い尺のほうが再生の成功率が低い理由も
     分かっていない。`PickPlaceAction` の経路 (approach の yaw 補間、終了判定の
     速度閾値など) を疑っているが未確認。

#### 探索の経緯 (同じ失敗を繰り返さないため)

* 置き先を「リンク番号の点を越える」で決めると、輪の大きさ・向き・鏡像の
  ばらつきに負けた (最高 8/64)。**輪の座標系** (原点 X、u = 輪の中心へ、
  v = edge A 側) で置き先を指定し、手ごとに作り直す形にして安定した。
* tuck を「edge A との交差 -> 先端」の延長線上へ運ぶ案は失敗した。尻尾は edge A の
  下へ浅い角度で入るので、延長線は edge A の反対側を上から越えてしまう。
* 成功例のパラメータはばらついていて (カオス的)、1 つの成功例の近傍を ±25% で
  揺らすと 47%、その近傍の傾向に沿って 1 歩動かすと 60% になった。

# 5. バージョン制への移行 (2026-09-24)

`main` と `feat/overhand-knot` で同じ `Isaac-Twisted-RL-Twist-v0` が別の実装を
指してしまっていた問題を解消するため、**タスクをバージョン制**にした。

    Isaac-Twisted-RL-Twist-v0   交差を 1 つ作る   (旧 main の実装)
    Isaac-Twisted-RL-Twist-v1   固結び           (§4.8 の実装)

以降の改良は既存バージョンを書き換えず、`v2`, `v3`, ... を足していく。

## フォルダ構成の変更

```
knot_tying/
├── common/     バージョン非依存の共有層 (mdp/ topology/ rope_model/
│               parallel_gripper/ rope_state.py env_cfg_base.py rope_task_cfg.py)
├── versions/   バージョンごとの配線 (v0/ v1/ に env_cfg.py と agents/ と README.md)
└── demos/      RL 環境から import されない独立スクリプト
```

旧 `knot_tying_env_cfg.py` は `common/env_cfg_base.py` になり、
**観測と報酬はそこから抜いて `versions/vN/env_cfg.py` へ移した**
(課題そのものなのでバージョンごとに変わるため)。
プリセット 4 種 x (通常/Play) の 8 クラスは
`common/rope_task_cfg.py` の `make_preset_cfgs()` が生成する。

## 「バージョン = 設定」という方針にできた理由

§4.8 の変更が **共有 MDP 層への純粋な追加だった**ため。
`git diff main..HEAD` で確認したところ `mdp/rewards.py` と
`mdp/observations.py` はどちらも「84 行追加・0 行削除」で、
`mdp/terminations.py` `mdp/phases.py` `mdp/events.py` `rope_state.py` は
バイト一致だった。v0 の項 (`crossing_progress` / `crossing_achieved` /
`first_crossing_feature`) がすべて残っているので、
**v0 を共有コードから再構成しても main と挙動が一致する**。

したがってコードを複製・凍結する必要がなく、バージョン間の差は
「どの項をどの重みで配線するか」だけで表現できる。
この性質を保つため、**共有層の項は追加のみ・削除改名しない**ことを
規約にした (`README.md` 参照)。

## 実装時に踏んだ注意点

- `import_packages` のブラックリスト `".mdp"` は**部分文字列一致**
  (`isaaclab_tasks/utils/importer.py` の `_walk_packages` で確認)。
  `common/mdp` も除外され続けるが、**フォルダ名を変えると除外されなくなり
  `list_envs` が壊れる**。
- `_walk_packages` は**パッケージの `__init__` しか import しない**
  (プレーンモジュールは列挙するだけ)。よって `demos/` を作っても
  デモ本体が Kit 起動前に読まれることはない。
- `make_preset_cfgs` の `__post_init__` で `super(type(self), self)` を
  使うと、Play 側から呼ばれたときに無限再帰する。基底クラスを閉包で
  固定して直接呼ぶこと。
- `experiment_name` をバージョンごとに分けた
  (`knot_tying_v0` / `knot_tying_v1`)。`--experiment_name` フラグは
  `cli_args.update_rsl_rl_cfg` が適用していないので効かない。cfg 側で指定する。
