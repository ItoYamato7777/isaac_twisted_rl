## 1. Step 1〜3 (完了): `common/topology/` パッケージ

ロープの 3D 点列から p-data を作る**純粋ロジック層**。`isaaclab` を import しないので、
Isaac Sim 無しでテストできる。

```
common/topology/
├── __init__.py            公開 API
├── representation.py      Point / Edge / Face / AbstractState (半辺構造と p-data)
│                          v3 で移植元の R1 / R2 / cross も移植した (§4.7)
├── intersections.py       バッチ化 2D 自己交差検出 (テンソル層)
├── state_2_topology.py    交差 -> AbstractState -> p-data (記号層)
├── polyline.py            ポリライン前処理 (節点生成・中心寄せ・細分・再標本化)
├── knot_detect.py         固結びの部分列判定・位相クラス・R2 除去 (v1 / v2-R2)
└── knot_graph.py          p-data グラフの BFS 距離 (v3)
```

### 使い方

```python
import torch
from isaac_twisted_rl.tasks.knot_tying.common import topology as tp

# (num_envs, num_links, 3) のリンク中心 -> (num_envs, num_links+1, 3) のポリライン
nodes = tp.polyline_from_link_centers(link_pos)

# テンソル層: バッチ / GPU。4096 環境で 1.6 ms
batch = tp.segment_intersections(nodes)
batch.count      # (num_envs,)          交差数
batch.writhe     # (num_envs,)          符号の総和
batch.data       # (num_envs, M, 4)     (seg_i, seg_j, over, sign)
batch.order      # (num_envs, M, 2)     交点の出現順 (1 始まり)

# 記号層: env ごとの Python。4096 環境で 94 ms。呼ぶ頻度を絞ること
p_datas = tp.p_data_from_batch(batch, short=True)   # ['1U2+_2O1+', ...]

# 可視化用: 交差の xy 座標を復元
xy = tp.crossing_positions(nodes, batch)            # (num_envs, M, 2), 無効は NaN
```

### 検証済みであること

- **原実装との一致**: ランダムなポリライン 600 本で twisted_rl の `state2topology` と突き合わせ、**全件一致**。
  (原実装の `find_new_intersections` には、「細分の反復で `num_of_points` が更新されず、折れ線の末尾が
  切り落とされる」バグがある。これを直したうえでの比較。未修正の原実装とは 600 本中 32 本で食い違うが、
  すべて原実装側の欠陥)
- 三葉結びが、離散化解像度 (40〜200 節点) によらず交差 3 つ / writhe −3 を返す
- 平行移動・z 軸回転・一様スケールで p-data が不変
- float32 (Isaac Lab の既定 dtype) でも float64 と同じ p-data
- **動いている物理の上でも正しい** (Step 5 で目視検証。§3)

### 移植元から意図的に変えた点

1. **shapely を使わない。** 線分交差は解析解で求める。`alpha` / `beta` が直接出るので、原実装のような
   距離比からの逆算が要らない。
2. **セグメント細分を廃止。** 原実装は「1 セグメントに交差 2 つ」を扱えず、セグメントを細かく割って
   回避していた。本実装は交差の弧長パラメータ `seg + alpha` を直接ソートして出現順を決めるので、細分が
   要らない。環境ごとに長さの変わる逐次ループが消え、**4096 環境で 2735 ms → 1.6 ms** になった。
3. **面の再構築の走査上限**を、定数 10 から辺の総数に変更。原実装は交差が 3 つ以上あると面をたどり切れなかった。
4. メソッド名 `addPoint` / `removePoint` は移植元の camelCase のまま残した。
   移植元のメソッドを後からコピーしてくるときの事故を防ぐため (v3 で実際に R1 / R2 / cross を移植した)。

## 2. Step 4 (完了): `common/rope_state.py`

`Articulation` に触れるのはこのファイルだけ。

```python
rope_body_names(num_links)                    # ["Link00", "Link01", ...]
resolve_rope_bodies(rope)                     # 名前で解決した紐順の body index
rope_polyline(rope, body_ids, env_origins)    # (num_envs, num_links+1, 3)

class RopeTopologyExtractor:
    update(rope)          # 毎ステップ回してよいテンソル層 (交差検出)
    count / writhe        # そのまま観測へ流せる量
    p_data(short=True)    # 呼ばれたときだけ記号層。update をまたぐキャッシュ付き
    crossing_positions()  # 可視化用の交点 xy
    check_link_order(rope)  # body 順序が壊れていないかの物理的検算
```

### body の順序: 実測結果 (2026-08-09, Isaac Sim 5.1 / RTX 3090)

「`rope.data.body_pos_w[:, k]` が `Link{k:02d}` である保証は無い」という懸念を、実際に確かめた。

| プリセット | num_bodies | `rope.body_names` | `find_bodies(..., preserve_order=True)` |
|---|---|---|---|
| `simple` / `stiff` / `twist` | 20 | `["Link00" ... "Link19"]` (定義順) | `[0, 1, ..., 19]` |
| `fine`   | 48 | `["Link00" ... "Link47"]` (定義順) | `[0, 1, ..., 47]` |

直線の初期姿勢での `body_pos_w[..., 0]` は単調増加した。デモ実行中の `check_link_order()` も、
**隣接リンク距離の max/median = 1.0000** を返した (D6 ジョイントは並進 3 軸をロックしているので、
順序が正しければこの比はぴったり 1 になる)。

**結論: 現状、body の順序は定義順と一致している。** それでも `rope_state.py` は名前で解決する経路を使う。
この一致はどこにも保証されていないうえ、崩れたときに**例外が出ないまま p-data だけが壊れる**という
最悪の壊れ方をするため。`check_link_order()` はその保険で、起動時イベントとしても走る。

## 3. Step 5 (完了): 台本デモ `demos/topology_debug.py`

ロープを台本どおりに操作しながら、p-data が変化した瞬間だけをログと図に残す。

```bash
uv run python -u src/isaac_twisted_rl/tasks/knot_tying/demos/topology_debug.py --rope twist --headless
# 出力 (既定は outputs/topology_debug/。.gitignore 対象)
#   events.log      p-data が変化した瞬間だけのログ
#   NNN_<tag>.png   xy 投影図。交点に "1O2+" (上の点 O 下の点 符号) を注記
```

主なオプション: `--motion {loop,random,hold}` / `--rope` / `--sim_hz` / `--rope_physx` /
`--subdivide` / `--check_every` / `--no_plot`。

### (a) 位相抽出は動く物理の上でも正しい

グリッパーが持ち上げた端が本体をまたぐと、`crossings=1 / p_data='1O2+_2U1+'` が出る。
図の z の色 (明るいほど上) と注記の O/U を突き合わせ、上下判定・符号・交点番号がすべて期待どおりで
あることを確認した。

### (b) 交差を作るには「たるみ」が要る

真っ直ぐなロープでは、掴んだ点 G からロープ上の点 K までの弧長は直線距離に等しい。一方、ハンドが
G から K の向こうへ回り込む経路は必ずそれより長い。そのため、経路長が弧長を超えた瞬間にロープが
張り切り、**端だけが本体を渡るのではなく、ロープ全体が平行移動する**。

台本は 2 段構えにしてある。1 手目でロープを大きく曲げてたるみを稼ぎ、2 手目でそのたるみの範囲内で
端を本体の上に渡す。渡し先は絶対座標ではなく、**リンク K の現在位置から実行時に決める**
(`GraspMove.over_link_frac`)。1 手目の結果は物理次第で毎回違うので、決め打ちでは本体を越えられない。

### (c) 「離したのに付いてくる」問題は物理パラメータで解決した

当初、指を開いて真上へ退避すると、ロープが指に残ったまま持ち上がり、作った交差が壊れていた。
対策は次の 2 つで、どちらもコードに反映済み。

| 対策 | 場所 | 内容 |
|---|---|---|
| ロープを柔らかく | `rope_specs.py` の `TWIST_YOUNGS_MODULUS` | `twist` のヤング率だけ 1.0e6 → **1.0e5 Pa**。曲げ剛性 EI はヤング率に比例するので、曲げ関節のばね定数も 1/10 になる。指を開いたときに、ロープが腰で引っかからなくなる |
| 指を常に全開に | `OPEN_RATIO` | 0.8 → **1.0**。接近時も離すときも全開。`common/mdp/phases.py` では、解放時の `RELEASE_RATIO` を `OPEN_RATIO` に統合した |

`twist` だけヤング率を下げたのは、**グリッパーで挟んで運ぶ用途に特化したプリセット**にしたため。
`stiff` / `fine` は比較用に元の剛性のまま残してある。後から足した `knot` は `twist` と同じ材料。
他のプリセットで学習するときは、この現象が再発しないか必ず確認すること。

| **行動の粒度** | **1 アクション = 掴む→運ぶ→離す 全部** (Options Framework 的) | 1 エピソード 3〜5 アクション。Step 5 の台本と同じ粒度 |
| **アクション空間** | ロープ相対 + `Δlink` (§4.1) | §4.1 に根拠 |

### 4.1 アクション空間: ロープ相対 + `Δlink`

```
grasp_link_id  離散 {2, ..., N-3}     掴むリンク
delta_link     離散 {-8, ..., +8}     → target_link_id = clip(grasp_link_id + delta_link, 0, N-1)
drop_x_rel     連続 ±0.15 L           target_link の現在位置からの xy 変位 (L = ロープ全長)
drop_y_rel     連続 ±0.15 L
drop_z_rel     連続 0 〜 3 ロープ直径  置くときの高さ (把持高さからの上乗せ)
end_yaw        連続 ±π                置き終わりの手首 yaw
```

計 **6 次元** (離散 2 + 連続 4)。`via_*` (中間経由点) は入れていない。
RSL-RL の PPO には離散ヘッドが無いので、実装では 6 チャネルすべてを連続 `[-1,1]` で受け取り、
`grasp_link` / `delta_link` は `PickPlaceAction` の側で丸める。
v3 では `drop_xy` を ±0.30 L に広げた (§4.8.10)。

#### なぜ「置く先」を絶対座標にせず、リンク相対にするのか

Step 6 の設計で最も重要な判断なので、根拠を全部書いておく。

1. **人間が設計した最良の手順ですら、リンク相対でしか書けなかった。** Step 5 の台本の 2 手目は、
   渡し先をリンク K の現在位置から実行時に決めている。1 手目の結果が物理次第で毎回違うので、
   絶対座標の決め打ちでは本体を越えられなかった。これが一番強い経験的根拠。
2. **pick&place の粒度では、離した瞬間にロープが物理で動く。** 次のアクションを決める時点で、
   リンク位置は前回と違う。置き場所を絶対座標で持つ意味がほぼ無い。
3. **絶対座標にすると「微小操作」の学習が逆に難しくなる。** 「リンク i を 2 cm 右へ動かす」という
   同じ意図が、リンク i の現在位置によって毎回違う出力値になる。リンク相対なら、この引き算が
   座標系のレベルで埋め込まれる (object-centric action space)。
4. **キネマティックハンドなので、絶対座標を使う利点が無い。** 可達領域の制約が無い。

#### なぜ `target_link_id` そのものではなく `Δlink` にするのか

- `grasp_link_id` と `target_link_id` を独立に選ばせると、N×N (20 リンクなら 400 通り) の離散ペアになる。
  `Δlink` なら 20×17 で済む。
- `Δlink` は「隣を掴む」「8 個先を狙う」という**状況によらない意味**を持つので、方策が汎化しやすい。

#### 「1 アクションで必ず位相が変わってしまうのでは」への回答

変わるかどうかは、`drop_*_rel` の範囲と `Δlink = 0` を許すかで決まる。

- `delta_link = 0` → 掴んだリンクのすぐ近くに置き直す = **微調整モード**
- `delta_link = ±8` → 本体の向こう側へ渡す = **位相を変えるモード**

「少しずつ操作する」は、アクション内の微小変位ではなく、**複数回の pick&place** として表現される。
Step 5 の台本 (1 手目: たるみ作り / 2 手目: 渡す) がまさにこれ。

#### 検討したが採らなかった案: パラメトリック曲線生成

`[grasp_link_id, target_link_id, approach_height, curve_radius, twist_yaw_angle]` という案。
「たるみを作る」ことを軌道の形として直接パラメータ化していて、§3(b) の幾何と相性が良い。
ただしこの案も始点・終点の指定を必要とし、`via_*` を曲線パラメータに圧縮した版と見なせる。
まず次元の少ない版で始め、必要になったら足すことにした。

#### 端リンクを除外する理由

端ちょうどを掴むと、接触面積が足りずに滑る。そのため `grasp_link_id` は `{2, ..., N-3}` に制限する。
`target_link_id` の側は範囲を絞る必要が無いので、`{0, ..., N-1}` に clip する。

### 4.2 最初の報酬 (交差 1 つを作って残す)

p-data は離散量なので、一致 / 不一致だけでは勾配が出ない。密報酬と併用する
(実装した重みは [v0 README](versions/v0/README.md))。

**最重要: 成功判定は必ずハンドを退避させた後に測ること。** そうしないと「ハンドで吊って交差を
見せかける」方策を学習する。§3(c) で「離すと付いてくる」問題は解決したが、報酬の測定タイミングは
それとは別に明示的に押さえておく必要がある。

ログには `rope_zmax` と `finger_gap` も出すこと。この 2 つを一緒に見ないと、「ハンドが吊っているだけ」を
「交差が残った」と取り違える。

### 4.3 `common/mdp/` の実装

Isaac Lab の manager-based の作法に従う。

**観測は p-data 文字列を使わない。** テンソル層 (`IntersectionBatch`) の数値をそのまま流す
(文字列の生成は 4096 環境で 94 ms、テンソル層は 1.6 ms)。p-data 文字列が要るのは、ログと Play の表示だけ。

**山場は `actions.py`。** 台本デモの `grasp_move()` は、1 手をフェーズごとに**逐次的に**実行している。
RL では全環境が並列に別々のフェーズにいるので、フェーズ ID と経過時間を `(num_envs,)` のテンソルで持つ
ステートマシンに書き換えた (`common/mdp/actions.py` + `common/mdp/phases.py`)。
フェーズはデモの 13 個を 12 個に整理した。デモの尺 (1 手 11.4 s) は目視デバッグ用に余裕を持たせた値なので、
学習用には詰めてある (尺の変遷は [`common/README.md`](common/README.md) §2)。

### 4.4 退化時の扱い (解決済み)

観測・報酬・終了判定をすべてテンソル層だけで組んだ結果、`intersections_to_topology` を呼ぶコードが
学習ループのどこにも無くなった。したがって、そこで `ValueError` は発生しえない。

### 4.5 NaN 対策 (解決済み): 240 Hz で回す

`twist` / 16 環境 × 10 手 / ランダム方策での発散率の実測:

| 設定 | 発散率 |
|---|---|
| 120 Hz | 11.2% |
| **240 Hz** | **1.2%** ← 採用 |
| 240 Hz + `make_rope_physx_cfg` | 3.8% |

120 Hz では、把持中の接触でロープの速度が 60〜175 m/s (正常時は 1 m/s 程度) まで跳ね上がり NaN になった。
原因は、`rope_cfg.py` の `max_depenetration_velocity` が **240 Hz を前提に**スケールされていること
(`_SIM_HZ_REF = 240.0`)。120 Hz では 1 ステップの押し戻し量が倍になり、「半径の 40% 以上は押し戻さない」
という前提が崩れる。`make_rope_physx_cfg` を併用すると却って悪化するのは、シーン全体の接触設定を変えて
グリッパーの押し付け力にも影響するため。

残った発散は、終了項 `diverged` がその場で reset し、報酬 `failure` が罰を与える経路で吸収する。

プリセット別 (240 Hz, ランダム方策 20 手): `twist` / `simple` / `stiff` は発散 0、`fine` のみ 20 手あたり
1〜2 回。`fine` で本格的に学習を回すなら、さらに `sim.dt` を詰める必要がある。

### 4.6 実装中に判明したこと (2026-09-10)

**(a) アクションの次元。** 当初の設計書は「計 7 次元」と書いていたが、数え間違いで、正しくは 6 次元 (§4.1 は修正済み)。

**(b) 離散アクションは連続チャネルの量子化で表した。** RSL-RL の PPO は連続ガウス方策しか持たない。
方策から見れば連続、環境に入る値は離散なので、§4.1 の設計意図は保たれている。

**(c) 報酬の重みは `step_dt` で割る必要があった。** `RewardManager.compute()` は各項に `dt` を掛ける。
1 env ステップ = 1 手 (数秒) なので、そのままでは重みが数倍になる。
`KnotTyingEnvCfg._rescale_reward_weights` が自動で割る。

**(d) 抽出器のキャッシュは reset 時に捨てる必要があった。** `ManagerBasedRLEnv.step()` は
`terminations -> rewards -> _reset_idx -> observations` の順に処理する。reset された環境の観測が
reset 前の形状のままになるので、`PickPlaceAction.reset()` から `invalidate_extractor()` を呼ぶ。

**(e) 摩擦材の bind はマルチ env 対応が要る。** `bind_physics_material` は正規表現を受け付けない。
そのため env ごとに展開してから bind する。取りこぼすと、**例外は出ないがロープが指をすり抜ける**。

**動作確認:** 4 プリセットすべてでランダム方策が完走した。ランダム方策でも交差が実際に生成され、
床に落ちた状態で残った (`crossings=1`, `zmax≈0.028` = ロープ直径の約 1.4 倍)。

#### 追記 (2026-09-12): 1 イテレーションの実時間が長すぎる

64 環境 × 10 ステップの 1 イテレーションに約 185〜200 秒かかり、2000 iteration では 100 時間を超える
見積もりになった。原因は「1 RL ステップ = pick&place 1 手」という設計そのもの。
移動系フェーズだけを詰めると、**1 手 5.0 s → 2.86 s でも把持成功率・交差生成率はほぼ変わらなかった**
(`PhaseDurations` の docstring)。`num_envs` を増やすのも有効 (GPU 並列なので、1 イテレーションの実時間は
ほぼ変わらずに経験量が増える)。

## 4.8 Step 7: 固結び (overhand knot) への拡張 → v1 (2026-09-15)

Step 6 の「交差 1 つ」から、最終目標の**固結び (三葉結び、交差 3 つ)** へ引き上げた。
移植元の構成 (記号プランナ + 単一の Reidemeister スキル) は採らなかった。
v1 の学習は失敗し、その後の経緯は v2 / v2-R2 / v3 の README にある。

### 4.8.1 なぜ移植元の構成をそのまま使わないか

移植元 TWISTED-RL は、**結び目そのものを一度も報酬にしていない**。報酬は
`{+1 目標位相に一致 / -1 それ以外へ変化 / 0 不変}` の疎報酬で、**位相が変わった瞬間にエピソードが終了**する。
固結びは、記号 BFS プランナが単一の移動スキルを 3 回連鎖させて組み立てる。

これを支えているのが **HER** と、**replay buffer を次段の初期状態プールにするカリキュラム** (G0→G1→G2)。
どちらも **off-policy (SAC) が前提**で、本リポジトリの on-policy PPO には載らない。

→ v1 では報酬ラダーを HER の代替と位置づけた。ただし、初期状態プールの考え方自体は PPO でも使えることが
後で分かり、v3 の到達状態アーカイブとして取り込んだ (Report §5.3)。

### 4.8.2 固結びはテンソル層だけで判定できる

移植元の BFS で、**到達可能な 3 交差状態 528 個を全列挙**して調べた。固結びは次の 3 条件で厳密に特徴づけられる。

1. 交差数が 3
2. **partner gap がすべて 3** (`|order[...,0] - order[...,1]| == 3`)
3. **符号がすべて同じ** (`|writhe| == 3`)

528 個中この 3 条件を満たすのはちょうど 4 個で、固結びの p-data 4 通り (キラリティ 2 × 走査方向 2) と
完全に一致する。

**条件 2 だけでは足りない** (16 個残る)。**条件 3 だけでも足りない**。独立した R1 ループ 3 つが
`1U2+_2O1+_3U4+_4O3+_5U6+_6O5+` で同符号になってしまうため。**両方が必要**。

→ 94 ms の記号層を使わずに済む。

### 4.8.3 厳密な `交差数 == 3` は実機で使えない

三葉結びの尻尾に小さなループが 1 つ付くだけで、交差数は 7 に増える。gap も `[3,3,3]` から
`[5,5,9,9,3,5,1]` へ変わり、**すべての点番号が振り直される**。20 リンクのたるんだロープでは、これが常態になる。

そこで **部分列 (subsequence) 判定**にした。「交差の k 個組のうち、**その k 個だけで番号を振り直したとき**に
gap がすべて k かつ同符号になる組が存在するか」を見る。

| 入力 | 交差数 | 判定 |
|---|---|---|
| 三葉結び (きれい) | 3 | True |
| 三葉結び + 尻尾ループ | 7 | **True** (厳密判定では False) |
| 結ばれていないコイル | 3 | False |
| ランダムロープ 600 本 | 0〜5 | 誤検出 **0 %** |

実装は `common/topology/knot_detect.py`。env ごとの Python ループを持たない完全ベクトル化。
探索するのは交差の先頭 8 スロットまでだが、その前に gap 1 の交差 (どの部分列でも条件を満たさない) を
後ろへ回してある (v3 で修正。Report §6.3)。

後に、この部分列判定だけでは「輪を丸ごと跨いだだけ」の状態も C2 と判定されてしまうことが分かった。
v2-R2 で、R2 除去を先に掛けるよう修正した ([v2-R2 README](versions/v2_r2/README.md))。

### 4.8.4 報酬は位相クラスのラダー + ポテンシャル整形

`crossing_progress` (Δ交差数) には「R1 を 3 回ひねれば交差数 3」という抜け道がある。そこで交差数ではなく
**位相クラス** (0: 交差なし / 1: 交差 1 つ / 2: 絡み 2 交差 / 3: 固結び) を段にし、ポテンシャル整形
`F = γΦ(s') − Φ(s)` で登らせる。段の表、ポテンシャル整形にした理由、γ を PPO と一致させる必要性は
[v1 README](versions/v1/README.md) §1 にまとめてある。

### 4.8.5〜4.8.7 観測の修正・ハイパーパラメータ・動作確認

[v1 README](versions/v1/README.md) に移した (§1 の変更表、`crossing_features` のバグ修正、§4 の動作確認)。

### 4.8.8 整形報酬を検証するときの注意 (実際に踏んだ罠)

`knot_class_shaping` が正しいかを確かめるとき、**`env.step()` から返ってきた後に位相クラスを読んではいけない**。
次の 2 つの理由で、「報酬が使った値」とは違うものを見てしまう。

1. **reset のタイミング。** `ManagerBasedRLEnv.step()` は `termination -> reward -> _reset_idx -> observation`
   の順に処理する。終了した env は、報酬計算の後にロープが初期姿勢へ戻る。そのため step 後に読むと、
   `Φ(s')` が reset 後の値になる。
2. **`_episode_sums` は reset でゼロクリアされる** (`reward_manager.py` の `reset()`)。
   エピソードをまたいで積算値を比較すると、必ずずれる。

正しい検証方法は、報酬関数自体を差し替えて、**報酬が計算されるその瞬間に** `Φ(s)` と `Φ(s')` を捕まえること。
実際にそうすると、誤差は厳密に 0 になる。

素朴に step 後に読んだ版では、最大 0.455 のずれが出た。しかも、終了した env が無いステップでもずれた
(抽出器が `common_step_counter` でスタンプされているので、どのタイミングで呼ぶかで返る batch が変わる)。
**報酬のバグではなく検証方法のバグ**だったが、気付きにくいのでここに残す。

### 4.8.9 学習を回す前に確認すること (ゲート)

* **ゲート 1: 台本で固結びが結べるか。** これが通らなければ、報酬をどう設計しても PPO は学習できない。
  失敗したら、まず `GraspLimits.drop_xy_rel_frac` を 0.15 → 0.30 に広げること
  (`drop_xy_max` = 0.123 m は、最小ループ周長 0.251 m の半分しかない)。
  → **2026-09-27 に通過** (§4.8.10)。予想どおり 0.30 が必要だった。
* **`num_envs` のスループットを実測すること。** 64 env だと 1 イテレーションに 185〜200 秒かかる。
  ロープの物理は GPU 並列なので、`num_envs` を増やすのが他のどの最適化よりも効く。
  → **2026-09-28、VRAM 実測のみ実施**: RTX 3090 (24 GB) で 4096 env のシーン構築時ピークは
  約 10 GB。既定値を 1024 → 4096 に上げた (`env_cfg_base.py`)。イテレーション時間そのものの
  実測はまだ (p-data 生成が 4096 env で 94 ms/回かかるので、観測・ログの呼び出し頻度次第では
  そちらがボトルネックになりうる。8192 まで上げる前に要確認)。
  → **2026-09-30 に実測** ([v4 README](versions/v4/README.md) の「学習速度」)。時間のほぼ全部が
  PhysX で、1 物理ステップ ≈ 34 ms の固定費 + 0.019 ms x 環境数 (ソルバの位置反復 16)。観測・報酬・
  p-data は誤差程度。固定費の正体はソルバの反復で、環境数を増やす効果は 4096 でほぼ頭打ち
  (8192 でも +20% 程度の見込み)。v4 は反復 8・1 iteration 4 手にして、約 20 分 -> 約 3 分にした。
* **学習中は、class 別に層別した発散率を見ること。** 交差数が増えると自己接触が超線形に増えるので、
  集計値では class 3 だけの発散増が埋もれる。v2-R2 以降は `Curriculum/topology_log/div_cls*` に出ている。

### 4.8.10 ゲート 1 の結果 (2026-09-27): 台本で固結びは結べる

**結論: 通った。ただし `twist` では長さが足りず、新プリセット `knot` が要る。**
6 次元の行動空間で再生するには、`drop_xy_rel_frac` の拡大とフェーズの尺の延長も要る。
**この 3 点は v3 で配線した** ([v3 README](versions/v3/README.md))。

検証スクリプトは `demos/overhand_script.py` (台本の中身と使い方は docstring)。学習環境をそのまま
`gym.make` し、ハンドだけを台本で動かす。128 環境で台本のパラメータを ±25% 揺らし、ハンドを退避させてから
**R2 除去後の位相**で判定した。

#### 台本 (5 手)

slack (たるみ) → loop (輪。先端側が上) → tail (先端を輪の外側へ) →
**cover (輪の片側 edge A を掴んで、尻尾の上に被せる)** → tuck (先端を、輪の反対側 edge B の上へ)。
pick&place では掴んだ部分が必ず上になる。そのため固結びの「下」は、cover のように**輪の側を動かして**
しか作れない (Report §5.4 の予想どおり)。

#### 成功率 (固結び / 128 環境)

| 条件 | `twist` (20 リンク) | `knot` (28 リンク) |
|---|---|---|
| 台本, 運搬高さを手ごとに調整, 7.8 s/手 | 23 (18%) | 77 (60%) |
| 台本, **運搬高さ 0.20 m 固定** (学習と同じ), 7.8 s/手 | 0 (`knot` 用の台本は移らない) | **122 (95%)**, 発散 0 |
| 同上, 3.2 s/手 (descend/lift/lower 0.3 s, carry 0.6 s) | — | **116 (91%)**, 発散 3 |
| 同上, 学習の尺 (v2 `SHORT_DURATIONS`, 2.44 s/手) | — | carry 0.35 s のままでは 1 手目で 13/32 が発散 |
| 6 次元行動で再生 (`env.step`), 7.8 s/手, `drop_xy` ±0.15 L | — | 36 (28%) |
| 同上, 3.2 s/手 | — | 12 (9%) |
| 6 次元行動で再生, 7.8 s/手, **`drop_xy` ±0.30 L** | — | 54 (42%), 発散 19 |
| 同上, 3.2 s/手 | — | **84 (66%)**, 発散 9, クリップ 0 (1 手目を除く) |

#### 分かったこと

1. **長さが決め手。** 固結びは、本体 ~8 / 輪 ~12 / 尻尾 ~8 リンクを使う。20 リンクの `twist` では、tuck の
   時点で輪の中の尻尾が 2〜3 リンクしか残らない。持ち上げると edge A の下から抜けて C1 に戻ってしまう。
   `knot` は、`twist` と材料・太さを同じにして 28 リンクに延ばしただけ。1 リンクの物理が同じなので、把持・
   「離すと付いてくる」対策・発散しにくさをそのまま引き継ぐ。根拠は `rope_specs.KNOT_NUM_LINKS`。
2. **運搬高さ 0.20 m 固定は障害ではない (むしろ良い)。** 被せる手・通す手を低く運ぶ台本 (60%) より、
   全部 0.20 m の台本 (95%) のほうが成功した。Report §5.6 / P3-1 の「z_max を行動に入れる」は、少なくとも
   固結びには不要。
3. **`drop_xy_rel_frac` = 0.15 は足りない (§4.8.9 の予想どおり)。** cover の置き先は、128 環境中 79〜97 で
   target リンク ±8 本 + ±0.15 L の外にあり、クリップされて輪ごと崩れた。
4. **`knot` は学習の短い尺で発散する。** 原因は運搬速度 (carry 0.35 s で 0.5 m 以上動かし、1.14 m の本体を
   引きずる)。carry 0.6 s にすると、1 手目の発散は 13/32 → 0/32 になった。ソルバ反復 32・指ゲイン 2 倍は
   効かなかった。descend が速いと、結び目の上へ指を降ろす手でも発散する (tuck の descend/close で 18/128)。
5. **R2 版のラダーは cover の手を評価できない。** cover の直後は、多くの場合 edge A のたるみが尻尾を 2 回
   またいだ `1U4+_2O5+_3O6-_4O1+_5U2+_6U3-` になる。これは R2 除去すると C1 (`1U2+_2O1+`) と同じになるが、
   この状態から tuck で約 7 割が固結びになる。v2-R2 の報酬では「cover を打っても何も起きていない」ように
   見える。→ v3 の BFS 距離ポテンシャルでこの状態を段として数えるようにした (v3 README の P1-3)。
6. 台本の途中状態 (輪 / cover 後 / C2) は、到達状態アーカイブの初期データにそのまま使える (未実装)。
7. **6 次元の行動空間でも結べる (66%)。** 条件は `drop_xy_rel_frac` 0.30 と 3.2 s/手の尺。1 手目 (たるみ) の
   置き先は ±0.30 L でも届かずクリップされるが、クリップ後の形でも後続は成立する
   (届く範囲に台本を直すと 49/128 に下がった)。
   * 共有層の既定値 (`GraspLimits` / `SHORT_DURATIONS`) は変えていない。v0〜v2-R2 の挙動を変えないため。
     v3 では `KnotTyingEnvCfg.grasp_limits` と `KNOT_DURATIONS` を通して配線した。
   * **未解明:** 同じ尺でも、`env.step()` で再生すると台本モードより発散が多い
     (3.2 s/手で 9 vs 3、7.8 s/手で 19 vs 0)。遅い尺のほうが再生の成功率が低い理由も分かっていない。
     `PickPlaceAction` の経路 (approach の yaw 補間、終了判定の速度閾値など) を疑っているが、未確認。

#### 探索の経緯 (同じ失敗を繰り返さないため)

* 置き先を「リンク番号の点を越える」で決めると、輪の大きさ・向き・鏡像のばらつきに負けた (最高 8/64)。
  **輪の座標系** (原点 X、u = 輪の中心へ、v = edge A 側) で置き先を指定し、手ごとに作り直す形にして安定した。
* tuck を「edge A との交差 → 先端」の延長線上へ運ぶ案は失敗した。尻尾は edge A の下へ浅い角度で入るので、
  延長線は edge A の反対側を上から越えてしまう。
* 成功例のパラメータはばらつく (カオス的)。1 つの成功例の近傍を ±25% で揺らすと 47%、その近傍の傾向に
  沿って 1 歩動かすと 60% になった。

## 6. バージョン制への移行 (2026-09-24)

`main` と `feat/overhand-knot` で、同じ `Isaac-Twisted-RL-Twist-v0` が別の実装を指してしまっていた。

### 「バージョン = 設定」という方針にできた理由

§4.8 の変更が、**共有 MDP 層への純粋な追加だった**ため。`git diff main..HEAD` で確認すると、
`mdp/rewards.py` と `mdp/observations.py` はどちらも「84 行追加・0 行削除」で、`mdp/terminations.py` /
`mdp/phases.py` / `mdp/events.py` / `rope_state.py` はバイト一致だった。v0 の項がすべて残っているので、
**v0 を共有コードから再構成しても main と挙動が一致する**。

したがってコードを複製・凍結する必要がなく、バージョン間の差は「どの項をどの重みで配線するか」だけで
表現できる。この性質を保つため、**共有層の項は追加のみとし、削除・改名しない**ことを規約にした。

### 実装時に踏んだ注意点

- `make_preset_cfgs` の `__post_init__` で `super(type(self), self)` を使うと、Play 側から呼ばれたときに
  無限再帰する。基底クラスを閉包で固定して直接呼ぶこと。
- `--experiment_name` フラグは `cli_args.update_rsl_rl_cfg` が適用していないので効かない。
  cfg の側で `knot_tying_vN` を指定する。
- `import_packages` の注意 (`mdp` というフォルダ名を変えない、など) は README の
  「注意: Kit 起動前に import されるファイル」にまとめてある。
