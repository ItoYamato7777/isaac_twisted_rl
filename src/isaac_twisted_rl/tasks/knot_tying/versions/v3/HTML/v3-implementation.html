02env.step 1 回 = pick&place 1 手

この環境の要は、Isaac Lab の decimation (1 回の env.step() で回す物理ステップ数) を「1 手ぶんの物理ステップ数」にしていることです。方策は 1 手に 1 回だけ行動を出し、その 1 手を実行し切ってから、終了判定・報酬・観測が 1 回ずつ計算されます env_cfg_base.py。

この順序は v3 の設計に 3 か所で効いています。

  1. 形の保存を「報酬項」でやる。報酬は reset より前に計算されるので、手の終わりの形 (reset される前の形) を確実に読めます。そこでアーカイブへの保存 record_archive は、常に 0 を返す報酬項として登録してあります。重みを 0 にすると RewardManager が呼ばなくなるので、重みは 1.0 です。
  2. アーカイブからの復元は reset_all の後ろに置く。設定クラスに書いた順がそのまま適用順になります。まず基底の reset_all がロープとハンドをまっすぐな初期状態に戻し、その後で reset_from_archive が選ばれた環境のロープだけを上書きします。
  3. 観測は復元後の形で計算する。PickPlaceAction.reset() が位相の抽出器のキャッシュを捨てるので、直後の観測はアーカイブから書き込んだ形で計算されます。

報酬の重みは __post_init__ で 1 env ステップの秒数 (step_dt) で割ってあります。Isaac Lab の RewardManager が各項に dt を掛けるためで、割っておくと設定に書いた値がそのまま「1 手あたり」の報酬になります。このページの報酬の値は、すべて 1 手あたりです。

03ロープとハンド

ロープ: Knot プリセット

PhysX の articulation で作ったカプセルの鎖です。28 リンク、全長 1.14 m、直径 20 mm。材料と太さは v2-R2 までの Twist と同じで、リンクの数だけを 20 から 28 に増やしました。1 リンクの物理が同じなので、把持のしやすさや「離すと指に付いてくる」対策をそのまま引き継げます。

ハンド: キネマティックな平行グリッパ

腕はありません。手首の位置と姿勢を毎物理ステップ直接書き込んで動かします (速度も書き込まないと摩擦が効かず、ロープが滑り落ちる)。把持は摩擦だけです。指を「全閉」に指令し続けると、ロープの太さぶん閉じ切れず、PD 制御の定常偏差がそのまま把持力になります。

なぜ 28 リンクなのか

ゲート 1 では、学習環境をそのまま使い、ハンドだけを台本で動かして固結びを結びました (128 環境、台本のパラメータを ±25% 揺らす)。固結びは「本体」「輪」「尻尾」の 3 つの部分でロープを使い切ります。

シーンは既定で 1024 環境 (間隔 3 m)、物理は 240 Hz です。120 Hz に落とすと、把持中の接触でロープの速度が跳ね上がり発散率が 1.2% から 11.2% に上がったため、240 Hz のままにしてあります。

04行動: 6 次元で 1 手を決める

行動は 6 次元の連続値で、すべて [−1, 1] にクリップされます。PPO はガウス方策 (連続) しか持たないので、離散の量 (リンク番号) も連続値で受け取り、環境の側で丸めます mdp/actions.py。置き先は絶対座標ではなく、ロープ上の target リンクの今の位置からの相対で決めます。離した瞬間にロープが動くので、絶対座標で覚えても意味が薄いためです。

051 手の動き: 12 フェーズの状態機械

1 手は 12 個のフェーズの列です。全環境が同時に別のフェーズにいるので、フェーズ番号と経過ステップ数を環境ごとのテンソルで持ちます。各フェーズの中は smoothstep で補間し、始点と終点で速度が 0 になるようにしています (等速補間だと、端で速度が不連続になった慣性でロープが指から滑る)。

下の帯は、フェーズの長さを物理ステップ数 (240 Hz) に比例した幅で並べたものです。v2-R2 の帯は、全体の長さも比べられるよう v3 と同じ縮尺で描いています。

尺を延ばしたのは発散を抑えるためです。1.14 m の Knot を v2-R2 の尺 (carry 0.35 s) で運ぶと、ロープの大部分を 0.5 m 以上引きずることになり、1 手目で 32 環境中 13 が発散しました。carry を 0.6 s にすると 0/32 になりました。descend が速いと、結び目の上へ指を降ろす手でも発散します。

approach と clear の尺 0 は v2 から引き継いだものです。尺 0 のフェーズは 1 物理ステップになり、補間の終点がそのまま書き込まれ、速度の指令は 0 になります。つまり「移動」ではなく「位置の書き換え」で、0.30 m (ロープ直径の 15 倍) の高さなのでロープには触れません。

06観測: 129 次元

観測は v2 から項も並びも変えていません。ロープが 28 リンクになったぶん、リンク位置が 60 次元から 84 次元に増えただけです mdp/observations.py。critic も方策と同じ観測を見ます (特権観測はありません)。

07位相の判定: 交差から「段」と「Φ」へ

報酬・終了・アーカイブ・観測はどれも、毎手の終わりに測る「ロープの位相」から作られます。p-data の文字列を作ると 4096 環境で 94 ms かかるので、学習中は文字列を作らず、テンソルのまま (4096 環境で 1.6 ms) 判定します topology/knot_detect.py。

段 (class) の定義

段は上から順に判定します。どの段にも当てはまらなければ 0 です。

段呼び名条件 (R2 除去後の交差で判定)

  • 部分列判定: 実物のロープでは、固結びの尻尾に小さな輪が 1 つ付いただけで交差数が 7 になり、番号がすべて振り直されます。「交差数 == 3」で判定すると本物の固結びを取りこぼすので、「交差の k 個組のうち、その k 個だけで条件を満たす組があるか」を見ます。
  • R2 除去 (v2-R2 で導入): 部分列判定は、先端で輪を上から跨いだだけの状態 (偽の C2) も C2 と判定してしまいます。両方の紐の上で隣り合う 2 交差で、同じ紐が両方とも上なら、その 2 交差は二角形を作っていて持ち上げれば外れる (Reidemeister II) ので、先に取り除きます。上下が交互になる組は消さないので、固結びが消えることはありません。
  • 8 スロット打ち切りの修正 (v3、全バージョンに効く): 部分列の探索は交差 8 個までに打ち切ります。以前は頭側の 8 個をそのまま使っていたため、交差が 9 個以上あると結び目が紐のどちら側にあるかで結果が変わりました。gap 1 の交差 (R1 のねじれ) はどの部分列でも条件を満たさないので、打ち切る前に後ろへ回すようにしました。結果は変えずに見落としだけが減ります。

09BFS 距離のポテンシャル P1-3

整形報酬 F = γΦ(s′) − Φ(s) は、Φ が「ゴールへの近さ」をよく表すほど役に立ちます。v2-R2 の Φ は 4 段のラダー (0, 0.35, 0.70, 1) でした。v3 は、TWISTED / TWISTED-RL が高レベルの計画に使う p-data のグラフを起動時に列挙し、各状態から固結びまでの最短手数 d を表にして、Φ に使います topology/knot_graph.py。

Φ(s) = max( 1 − d(s) / 3 , 段(s) / 3 ) d(s) : p-data グラフ上で、s から「R2 除去後に固結びを含む状態」までの最短の移動回数 (移動 = R1 / R2 / Cross。d(自明) = 3) 段(s) : R2 除去後の段 0〜3 (表に無い状態はこちらだけで決まる)

表の作り方

  1. 交差のない状態から、R1 / R2 / Cross の 3 種類の移動で幅優先に状態を広げ、交差 4 個以下の状態と辺をすべて列挙します。交差 0 / 1 / 2 / 3 / 4 の状態は 1 / 4 / 40 / 528 / 7968 個、合計 8541 個で、約 20 秒かかります (起動時に 1 回だけ)。
  2. そのうち「R2 除去すると固結びを含む」状態 (172 個) をゴールにし、辺を逆にたどる BFS で各状態の d を求めます。同じ p-data で面の構造だけが違う状態は、最小の d を取ります (実物のロープからは p-data しか取れないため)。
  3. 実行時は、交差の情報から p-data の文字列を作らずに int64 のキーを作り (交差数 3 bit + 点ごとに相手の番号 4 bit・上下 1 bit・符号 1 bit、最大 51 bit)、ソート済みのキーの表を GPU 上で二分探索します。

なぜ「R2 除去前・交差 4 個まで」なのか

最初は Report の案どおり、R2 除去後の p-data を交差 3 個まで BFS しました。しかし固結びに届く p-data は 13 個 (自明・輪 4・C2 4・固結び 4) だけで、経路上の値はラダーと完全に同じになり、何も足しませんでした。cover の後の状態は、R2 除去前の p-data で見て初めて「tuck 1 手で、R2 除去すると固結びになる 4 交差の状態へ行ける」とわかるので、除去前の p-data を 4 交差まで見る必要がありました。

なぜラダーとの max を取るのか

探索は交差 4 個で打ち切るので、4 交差の途中状態や、尻尾に余分な輪が付いた状態は表の上で「届かない」(値 0) になります。BFS の値だけを使うと、これらがラダーより低くなり、「ねじれを 1 つ足すと 0、2 つ足すとラダーの値」のような逆転が起きます。そこで BFS は加点にだけ使い、ラダーより下げないようにしています。

整形報酬の値の例 (γ = 0.95)

固結びで終わる手でも Φ(s′) は実際の値 1.0 のまま払います。終端のポテンシャルを 0 にすると、固結びを作った手に −Φ(s) の罰が乗ってしまうためです (発散のときとは逆の扱い)。

10段の初回ボーナス P1-2

v2-R2 は、段の条件を満たしている間毎手 +0.5 / +1.5 / +3.0 を払っていました。すると「1 手目で輪を作って、あとは維持するだけ」が強い局所解になり、判定に抜け道があればそれも毎手繰り返し悪用されます (v2 の偽の C2)。v3 の LadderProgressBonus は、同じ値を「そのエピソードで到達した最高段を更新した手」にだけ払います。

  • best はリセットで「未定」にし、最初の手で「手を打つ前の段」から初期化します。アーカイブから C2 で始めたエピソードは最初から best = 2 なので、もらえるボーナスは固結びの +3.0 だけです。
  • 段を飛ばして上がったら、飛ばした段のぶんも合計して払います (例: 輪 1 つ → cover の後 → 固結び なら、最後の手に +1.5 + 3.0 = +4.5)。
  • 段を落としてから登り直しても、2 度目は払いません。
  • 支払いの条件は終了判定と同じ (ロープが床に落ちている、発散していない) です。報酬が払われたのに続く・払われないのに終わる、ということが起きないようにそろえてあります。

divergedロープの座標が NaN / 高さ > 5 m / env 原点から水平に > 3 m / リンク速度 > 20 m/s終端

発散の閾値は、ランダム方策の実測 (512 環境 × 24 手) で、正常な手の終わりが水平 1.52 m・速度 3.3 m/s 以内、発散時が数十 m 以上・60〜175 m/s だったことから、正常側に 2 倍以上の余裕を取って決めたものです (v2-R2)。報酬の側はこの終了項の判定を読み直して「発散した手」を見分けるので、閾値はこの 1 か所にしかありません。

12到達状態アーカイブ P1-1

v2-R2 は毎回まっすぐなロープから始めていたので、C2 からの手を練習できるのは「偶然 C1 に着いたエピソードの残りの手」だけでした。v3 は、学習中に到達した C1 / C2 の形を保存しておき、reset の半分をそこから始めます。TWISTED の到達木や TWISTED-RL の初期状態の選び方 (Go-Explore 型) にならったものです mdp/archive.pystate_archive.py。

設計の細部

  • xy を重心からの相対で持つ理由: 復元のたびに重心を env 原点に置き直すためです。アーカイブから始めた環境の形がまたアーカイブに入る連鎖で、ロープが原点から離れていき、発散判定 (水平 3 m) に近づくのを防ぎます。
  • z 軸まわりに回してよい理由: 真上から見た図を回すだけなので、p-data (交差の順・上下・符号) は変わりません。同じ形でも向きの違う初期状態が得られます。
  • 復元の検算: 関節角を書き込んだ直後にリンクの位置を読むと Isaac Lab が順運動学を計算し直すので、その場で位相を測り、保存時の段と一致するかを restore_mismatch に数えます。0 に近くなければ復元が壊れています。
  • 重み C1 : C2 = 1 : 2: 交差の多い状態を優先する TWISTED の開始点の選び方にならいました。重みは空でない段の中で正規化します。
  • 評価への影響: アーカイブから始めたエピソードは途中の段から始まるので、成功率が水増しされます。方策の実力は、まっすぐなロープから始めたエピソードの成功率 scratch_success で見ます。Play では確率を 0 にして、常にまっすぐなロープから 12 手を打ちます。
  • アーカイブはプロセスのメモリにだけ持つので、--resume で再開すると空から始まります。

13学習器: PPO (RSL-RL)

v3 は環境側 (リセット・報酬・終了・ロープ・行動の範囲・尺) を変えた版なので、PPO のハイパーパラメータは効果を切り分けられるよう v2-R2 (= v2) から据え置いています v2/agents/rsl_rl_ppo_cfg.py。

3 つの変種

Isaac-Twisted-RL-Knot-v3 が MLP (学習の本命)、-RNN が GRU、-LSTM が LSTM (隠れ層 256、ミニバッチ 2)。環境は同じで、ネットワークだけを変えて比べるための登録です。

γ を共有する理由

ポテンシャル整形が最適方策を変えないという保証 (Ng ら 1999) は、整形に使う γ と方策の割引率が一致して初めて成り立つので、GAMMA を 1 か所で定義して両方から参照しています。

v2-R2 から暖機できない

観測が 105 → 129 次元に変わったので、v2-R2 のチェックポイントはそのままでは読めません。

確かめられたこと

アーカイブは最初の iteration から埋まり、復元した形の位相は全件一致した。固結びはアーカイブから始めたエピソードでだけ出ている (archive_success 0.075、scratch_success 0)。価値関数の損失は O(0.1) で、v2-R2 の最初の run のような発散は無い。3 つの切り分けの上書きと Play も動いた。

気になること

発散が多い。1 手あたり約 5% (div_cls0 3%、div_cls1 2%) で、12 手のエピソードの約半分が発散で終わる。ランダムな手が結び目の上へ指を降ろすなど乱暴なためと見ている。1 手 (env.step 1 回) に約 25 s かかり、v2-R2 の約 19 s に尺の延長 (×1.3) を掛けた値になっている。

この版で解決していないこと

  • 本番の学習は未実施。smoke test で配線が動くことだけを確かめた。
  • ゲート 1 の台本の途中状態 (輪 / cover の後 / C2) でアーカイブを初期化すれば、学習の最初からアーカイブを使える (Report P0-2)。未実装。
  • 推論時の探索 (Report P2-4)、対称性によるデータ拡張 (P2-1)、遷移ごとのスキルへの分解 (P3-4) は範囲外。
  • ゲート 1 で見つかった「同じ尺でも env.step() で再生すると台本より発散が多い」理由はまだわかっていない。

論文の仕組みとの対応、取り込めていない部分、この設計で起こりそうなことの考察は 「v3 と 3 論文の比較・考察」 にまとめています。
