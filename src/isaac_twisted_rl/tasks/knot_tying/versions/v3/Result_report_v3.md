## 0. 要旨

1. **まっすぐなロープから固結びを結べるようになった。** まっすぐなロープから始めたエピソードのうち固結びで終わった割合 (`scratch_success`) は、iteration 0 の 0.2% から iteration 150〜159 の平均 25% まで上がった。このリポジトリで固結びを学習できたのはこれが初めて。v2-R2 では固結びは 1 手あたり 0.004% しか出ていなかったが、v3 の iteration 159 では 3.3% だった。
2. **まだ頭打ちではない。** `scratch_success` は最後の 20 iteration でも 20 iteration あたり約 +4 ポイントのペースで伸びていた。予定の 2000 iteration のうち 160 (8%) で止まっている。
3. **失敗のいちばん大きな原因は発散。** エピソードの 37% が発散で終わる。1 手あたりの発散率は iteration 50〜60 で一度 2.9% まで下がったが、その後 6.0% まで戻った。段 2 (C2) から打った手の発散率が 1 手あたり約 13% と特に高い。
4. **アーカイブから始めたエピソードの成功率が、まっすぐから始めた場合を下回った。** 学習の前半はアーカイブ始まりのほうが成功率が高く、固結びの経験を早く集める役に立った。iteration 100 前後で逆転し、最後はまっすぐ 25% に対してアーカイブ 19% だった。アーカイブが全体としてプラスに効いているかは、`prob=0` の比較 run を回すまで判断できない。
5. **run は PhysX の "Patch buffer overflow" で iteration 159 に止まった。** 修正は b345065 で入っている。最新のチェックポイントは `model_150.pt`。1 iteration に約 19 分かかるので、残りの 1840 iteration を回すと約 24 日かかる。

- 平均エピソード長 (`Train/mean_episode_length`) は 9〜10 手から 5.9 手に縮んだ。成功と発散で早く終わるエピソードが増えたため。

### 3.2 手の後の位相の分布 (1 手あたり、R2 除去後)

| iteration | 段 0 | 段 1 (C1) | 段 2 (C2) | 段 3 (固結び) | 偽の C2 (`fake_c2`) | 交差数 (除去前 / 後) |

- 本物の C2 (`r2_c2`) は v2-R2 の 0.3% から 10.4% に、固結び (`r2_c3`) は 0.004% から 3.3% に増えた。ただし v2-R2 の値は `Twist`・6 手・アーカイブなしの iteration 0〜1 のものなので、条件はそろっていない。

- 部分列探索の打ち切り (`r2_trunc`) は 0.02% 以下で、無視してよい。

### 3.3 発散

| iteration | 1 手あたりの発散 (合計) | 段 0 から | 段 1 から | 段 2 から | エピソードが発散で終わる割合 |
|---|---|---|---|---|---|
| 0 | 5.6% | 5.0% | 6.2% | 33% | 29.5% |
| 50 | **2.9%** | 2.4% | 3.2% | 7% | 28.3% |
| 100 | 5.0% | 4.4% | 4.6% | 13% | 35.9% |
| 159 | 6.0% | 5.6% | 5.2% | **13%** | 37.4% |

(段 K からの率は `div_clsK / r2_clsK` で近似した。手を打つ前の段の分布を、手の後の段の分布で代用している。)

- iteration 50 までに発散は半分近くまで下がり、方策は「発散しない手」を一度は学んだ。その後、固結びを狙う手が増えるのと並行して、発散は元の水準以上に戻った。
- 段 2 (C2) からの手は、段 0・1 からの手の 2〜3 倍発散する。
- 1 手 6% で 12 手打つと、発散しないまま終わる確率は 0.94¹² ≈ 0.48。「エピソードの約 4 割が発散で終わる」という値とほぼ合う。

### 3.4 アーカイブ

- **復元は正しく動いた。** `restore_mismatch` は最後まで 0〜0.03% だった。4096 環境でも、復元した形の段は保存時とほぼ全件一致した。
- **すぐに満杯になった。** C1 は iteration 0 で、C2 は iteration 9 で容量 4,096 件に達した。`archive_frac` は約 0.50 で、設定どおり reset の半分がアーカイブ始まりになっている。
- **中身は毎 iteration 入れ替わる。** iteration 159 の分布 (C1 41%、C2 10%) と 1 iteration 49,152 手から計算すると、1 iteration に C1 が約 20,000 件 (容量の 4.9 倍)、C2 が約 5,100 件 (1.25 倍) 入る。アーカイブの中身は「これまでに到達した形」ではなく、ほぼ「直近の iteration の形」になっている。この件数には、アーカイブから始めて段が変わらなかったエピソードの形の再登録も含まれる。
- **成功率の逆転。** 20 iteration 平均で見ると、アーカイブ始まりの成功率は iteration 0〜79 ではまっすぐ始まりより高く (0〜19 で 4.4% 対 0.5%)、80〜99 でほぼ並び、100 以降は下回った (140〜159 で 19.1% 対 24.3%)。

### 3.6 速度

- 1 iteration 1,123 s、`Perf/total_fps` は 41〜47 手/秒。
- 1 環境・1 物理ステップあたりに直すと約 31,000 step/s (41 手/s × 759)。v2-R2 (1024 環境、`Twist`、585 step/手、53 手/s) も約 31,000 step/s だった。**環境数を 4 倍にしても、環境・物理ステップのスループットは変わっていない** (解釈)。ロープのリンクが 20 → 28 に増えたことを考えると、リンク単位では約 1.4 倍になっている。
- この速度で残りの 1840 iteration を回すと約 24 日かかる。

## 5. 結果からわかること

### 5.1 論文の中核 3 つを入れたことで、定式化の壁は越えた

v1〜v2-R2 は「交差 1 つは作れるが、その先に進めない」という、TWISTED の SAC+HER ベースラインと同じ壁に当たっていた (`paper/Report.md` §5.1)。v3 は 160 iteration で、本物の C2 が 1 手あたり 10%、固結びが 3.3% 出るところまで来た。まっすぐなロープから 12 手で結ぶ成功率も 25% ある。v3 で変えたこと (到達状態からのリセット、成功で終了 + 段の初回ボーナス、BFS ポテンシャル、`Knot` ロープと尺・置き先の範囲) の組み合わせは有効だった。ただし 4 つを同時に入れたので、**どれが効いたのかはまだ切り分けていない**。

### 5.2 次のボトルネックは発散

- エピソードの 37% が発散で終わり、固結びで終わる 25% より多い。
- 発散しなかったエピソードの中で固結びで終わった割合は 0.246 / (1 − 0.374) ≈ 39% になる。発散で失ったエピソードの一部が成功に変わるだけでも、成功率を大きく押し上げる余地がある (解釈。発散しなかった場合に成功したかどうかはわからない)。
- 段 2 からの手は 1 手あたり約 13% 発散する。結び目に近い、ロープが重なった状態で指を降ろす手が危ないのは、ゲート 1 の観察 (「descend が速いと、結び目の上へ指を降ろす手で発散する」) と合っている。
- 発散が iteration 60 から増えた時期は、交差数の増加 (除去前 1.3 → 2.0) と重なっている。ロープの自己接触が増えると接触パッチ数も増え、iteration 159 の "Patch buffer overflow" につながった。**overflow の手前で接触が取りこぼされていた可能性もある** (解釈)。この run の標準出力が残っていないので、PhysX の警告がいつから出ていたかは確認できない。

### 5.3 アーカイブは序盤の足がかりになったが、終盤の効き方は不明

- 序盤は、まっすぐ始まりではほとんど出ない固結びの経験を、アーカイブ始まりのエピソードが供給していた (iteration 0〜19 で 4.4% 対 0.5%)。これが方策の立ち上がりを助けたと考えるのが自然 (解釈)。
- 終盤はアーカイブ始まりのほうが成功率が低い。考えられる理由は 3 つある (どれも解釈)。
  1. アーカイブ始まりの 2/3 は C2 から始まり、C2 からの手は発散しやすい (1 手 13%)。
  2. アーカイブの C1 には `fake_c2` (20%) のような、R2 除去で C1 に数えられるが扱いにくい形が多く混ざる。
  3. 方策が「まっすぐから結ぶ手順」に特化し、ランダムに回転した途中の形からは続きを打ちにくい。
- アーカイブが全体としてプラスかどうかは、`env.events.reset_from_archive.params.prob=0.0` の run と比べないとわからない。

### 5.4 `fake_c2` の増加は必ずしも悪い兆候ではない

v2 では `fake_c2` の増加は「輪を跨ぐだけ」の報酬ハッキングを意味した。v3 では、偽の C2 には初回ボーナスが払われず、BFS の Φ も上がらない (ラダーの 1/3 のまま) ので、ハッキングの動機は無い。一方、「cover の後」は同じ `fake_c2` に数えられ、BFS では Φ = 2/3 と評価される。固結びが増えるのと並行して `fake_c2` が増えているので、**その多くは cover の後の状態の可能性が高い** (解釈)。確かめるには、BFS の段 (`BfsPotential.stage`) をログに足すか、Play で p-data を見る必要がある。

## 6. 未確認の点・注意

- **学習中の成功率は確率的な方策 (std 0.6) のもの。** Play (平均の行動) で `model_150.pt` を評価した成功率はまだ無い。決定的にすると上がるとも下がるとも言えない。
- **固結びの判定は寛容。** 部分列判定 + R2 除去なので、尻尾に余分な交差があっても成功と数える。Play で p-data と見た目を確認し、本当に結べているかを見るべき。
- **`--resume` するとアーカイブは空から始まる。** このログでは C1 は 1 iteration 目、C2 は 9 iteration 目で満杯になったので、再開の影響は数 iteration で消えると見込まれる (解釈)。
- **b345065 (PhysX のバッファ上限の引き上げ) の後に再開すると、物理の条件が変わる。** overflow が起きていなかった区間の力学は変わらないはずだが、overflow の手前で接触が落ちていた場合は、発散率が変わりうる。
- **2026-09-30 時点で GPU ドライバの不整合がある。** 18:52 に NVIDIA のドライバパッケージが 580.173.02 → 580.178.04 に更新され、読み込まれているカーネルモジュールは 580.173.02 のまま。`nvidia-smi` が "Driver/library version mismatch" で失敗する。再開の前に再起動が必要。

## 7. 次にやること (優先順)

1. **再起動して `model_150.pt` から再開する** (b345065 入り)。標準出力をファイルに残し、PhysX の overflow 警告を監視する。
2. **`model_150.pt` を Play で評価する** (まっすぐから・`prob=0`・256 環境程度)。確率的でない方策の成功率、発散率、固結びの p-data と見た目を確認する。
3. **発散を減らす。** 段 2 からの手の発散 (1 手 13%) が主な対象。descend / close の尺の延長、結び目の上に指を降ろす手の扱い、物理パラメータを段ごとの発散率を見ながら調べる。ゲート 1 で未解明のまま残った「`env.step()` で再生すると台本より発散が多い」問題とも合わせて調べる。
4. **切り分け run を回す** (`prob=0.0` / `knot_tied=null` / `potential=class`)。24 日の本番 run より先に、各 200 iteration 程度で v3 の 4 つの変更の寄与を比べる。
5. **ログを足す。** BFS の段 (cover の後を含む) の分布、成功したエピソードの手数、アーカイブ始まりのエピソードの開始段ごとの結果。v4 の `ResetToStage` のログは、この用途にそのまま使える。
6. **スループットを調べる。** 4096 環境で環境・物理ステップあたりの速度が 1024 環境と変わっていない。GPU と CPU のどちらで詰まっているかを確認し、環境数を増やす以外の高速化 (尺の見直し、描画・ログの頻度) を検討する。
